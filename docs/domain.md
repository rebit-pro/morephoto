# Описание предметной области: P2P-платформа Rebit

## 1. Общее описание

Rebit — P2P-платформа для торговли криптовалютами, интегрированная с биржей Bybit.
Пользователи подключают свой Bybit-аккаунт через API-ключи и получают возможность:

- Просматривать стаканы P2P-ордеров (покупка/продажа)
- Создавать собственные объявления (как маркет-мейкер)
- Управлять сделками: подтверждать оплату, выпускать активы, общаться в чате
- Управлять балансами и историей операций
- Получать уведомления о событиях

Система выступает как **прокси-слой** между пользователем и Bybit P2P API, обеспечивая:
удобный UI, локальное кэширование, аналитику, аудит и безопасность.

> ⚠️ **Ограничения Bybit P2P API:** ряд операций невозможен через API — создание сделки (ордера по чужому объявлению),
> отмена сделки, открытие арбитража, получение истории чата, получение списка платёжных методов пользователя.
> Эти ограничения обходятся через polling, локальное хранение и редирект в UI Bybit.
> Подробнее: [api.md § 9](api.md#9-ограничения-bybit-p2p-api).

## 2. Домены (Bounded Contexts)

### 2.1. Identity — Идентификация и доступ

**Ответственность:** аутентификация, авторизация, управление API-ключами Bybit.

**Ключевые понятия:**

| Понятие | Описание |
|---------|----------|
| **User** | Пользователь Bitrix (стандартная сущность b_user). Расширяется связями с доменными таблицами. |
| **ApiConnection** | Связка пользователя с Bybit: зашифрованные API Key + Secret Key, режим (testnet/mainnet), статус подключения. |
| **ConnectionStatus** | Статус подключения: `active`, `invalid`, `revoked`, `pending_verification`. |

**Инварианты:**
- У пользователя может быть только одно активное подключение к Bybit.
- API-ключи хранятся только в зашифрованном виде (AES-256).
- При каждом подключении выполняется тестовый запрос к Bybit API.
- Отключение API-ключей не удаляет историю сделок.

**Доменные события:**
- `ApiConnectionCreated` — подключен новый API-ключ
- `ApiConnectionRevoked` — подключение отозвано
- `ApiConnectionFailed` — тестовый запрос не прошёл

### 2.2. Exchange — P2P-торговля

**Ответственность:** стаканы ордеров, объявления, сделки, жизненный цикл ордера.

> ⚠️ Bybit P2P API позволяет: управлять объявлениями (CRUD), подтверждать оплату, выпускать активы,
> отправлять сообщения в чат, читать стакан и статусы ордеров.
> **Не позволяет:** создавать сделки по чужому объявлению, отменять сделки, открывать арбитраж, читать историю чата.

**Ключевые понятия:**

| Понятие | Описание |
|---------|----------|
| **CurrencyPair** | Валютная пара для торговли: token (USDT, BTC, ETH) + fiat (RUB, USD, EUR). |
| **PaymentMethod** | Способ оплаты: Тинькофф, Сбер, QIWI, банковский перевод и др. Локальный справочник, заполняется из ответов Bybit API. |
| **OrderBookEntry** | Запись стакана, кэшированная из Bybit: направление (buy/sell), цена, объём, лимиты, контрагент, методы оплаты. |
| **Advertisement** | Собственное объявление пользователя: тип (buy/sell), валютная пара, цена (фиксированная/плавающая), объём, лимиты, методы оплаты, условия. Полный CRUD через Bybit API. |
| **Trade** | Сделка между двумя сторонами. Rebit **не создаёт** сделки — они появляются на Bybit, Rebit обнаруживает их через polling и синхронизирует локально. |
| **TradeStatus** | Состояние сделки, синхронизируемое с Bybit: `pending_payment` → `payment_sent` → `payment_confirmed` → `completed` / `cancelled` / `disputed`. |
| **TradeChat** | Чат внутри сделки. Отправка через Bybit API (`order/message/send`), история хранится **только локально** — Bybit не предоставляет API для чтения истории. |
| **TradeMessage** | Сообщение в чате сделки: пользовательское, системное (смена статуса) или автоматическое (из скрипта). |
| **TradeChatScript** | Заготовленный сценарий автоматических сообщений трейдера. Привязывается к объявлению или выбирается вручную. При обнаружении новой сделки система автоматически отправляет шаги скрипта в чат от имени трейдера. |
| **TradeChatScriptStep** | Один шаг скрипта: текст сообщения + порядок + опциональная задержка перед отправкой. |

**Агрегаты:**
- **Trade** (корень) → TradeMessage[] — сделка владеет чатом.
- **TradeChatScript** (корень) → TradeChatScriptStep[] — скрипт владеет шагами.
- **Advertisement** (корень) — объявление пользователя. Может ссылаться на TradeChatScript для автоотправки при обнаружении сделки.
- **OrderBookEntry** — кэш, не агрегат; пересоздаётся при каждой синхронизации.

**Инварианты:**
- Объявление создаётся через Bybit API (`item/create`) — Bybit сам замораживает средства (`frozenQuantity`).
- Сделки обнаруживаются через polling `order/pending/simplifyList` и `order/simplifyList`.
- Таймер оплаты (по умолчанию 15 мин) и автоотмена — на стороне Bybit; Rebit только обновляет статус через polling.
- Сделка не может перейти в `completed` без прохождения `payment_confirmed`.
- Подтверждение оплаты (`order/pay`) и выпуск активов (`order/finish`) — доступны через Bybit API.
- Отмена сделки и открытие арбитража — **недоступны** через API; выполняются на стороне Bybit.
- В стакане отображаются только ордера не старше 5 минут.
- Чат сделки активен только пока статус ∈ {`pending_payment`, `payment_sent`, `payment_confirmed`, `disputed`}. После `completed` / `cancelled` — только чтение.
- Скрипт чата запускается автоматически при обнаружении новой сделки, если к объявлению привязан скрипт.
- Шаги скрипта отправляются последовательно с учётом задержки (`delay_seconds`).
- Антиспам: > 10 сообщений за 30 сек → блокировка отправки на 60 сек.
- Удаление скрипта обнуляет `UF_CHAT_SCRIPT_ID` в связанных объявлениях, но не затрагивает уже запущенные сделки.
- Сообщения контрагента, отправленные через UI Bybit, **не** видны в Rebit (нет API для чтения истории чата).

**Доменные события:**
- `TradeDiscovered` — обнаружена новая сделка через polling Bybit
- `TradePaymentSent` — покупатель отметил оплату (через Bybit API `order/pay`)
- `TradePaymentConfirmed` — продавец подтвердил получение (через Bybit API `order/finish`)
- `TradeCompleted` — сделка завершена (обнаружено через polling)
- `TradeCancelled` — сделка отменена (обнаружено через polling; отмена на стороне Bybit)
- `TradeDisputed` — открыт арбитраж (обнаружено через polling; арбитраж на стороне Bybit)
- `TradeMessageSent` — отправлено сообщение в чат (user/system/script через Bybit API `order/message/send`)
- `TradeChatScriptStarted` — запущен автоскрипт в чате сделки
- `TradeChatScriptDeleted` — удалён скрипт, связи с объявлениями обнулены
- `AdvertisementCreated` — создано объявление (через Bybit API `item/create`)
- `AdvertisementDeactivated` — объявление снято (через Bybit API `item/cancel`)

**Конечный автомат сделки (Trade State Machine):**

> Rebit **наблюдает** за переходами через polling Bybit API.
> Активные действия Rebit: подтверждение оплаты (`order/pay`) и выпуск активов (`order/finish`).
> Создание сделки, отмена и арбитраж — на стороне Bybit.

```
                          ┌────────────────────────────────────────┐
                          │  Bybit (polling order/pending + order/info) │
                          └─────────────────┬──────────────────────┘
                                            │
                    ┌───────────────────────▼───────────────────────┐
                    │            pending_payment (status=10)         │
                    │  Rebit обнаруживает через polling              │
                    └──────┬──────────────────────────┬─────────────┘
                           │                          │
               Rebit: order/pay              Bybit: timer / user_cancel
                           │                          │
                    ┌──────▼───────┐           ┌──────▼───────┐
                    │ payment_sent │           │  cancelled   │
                    │  (status=20) │           │  (status=40) │
                    └──────┬───────┘           └──────────────┘
                           │
               Rebit: order/finish
                           │
                    ┌──────▼───────┐
                    │  completed   │
                    │  (status=50) │
                    └──────────────┘

                    ┌──────────────┐
                    │   disputed   │  (status=30, Bybit-side only)
                    │              │  может перейти в completed или cancelled
                    └──────────────┘
```

### 2.3. Wallet — Кошелёк и балансы

**Ответственность:** балансы пользователя, синхронизация с Bybit, транзакции, локальный учёт.

> **Связь с Bybit API:** Bybit предоставляет **только чтение** балансов (`GET /v5/asset/transfer/query-account-coins-balance`).
> При создании объявления Bybit **сам замораживает** средства (`frozenQuantity` в ответе `item/personal/list`).
> Wallet синхронизирует данные Bybit → локальную БД. При расхождении — приоритет данным Bybit.

**Ключевые понятия:**

| Понятие | Описание |
|---------|----------|
| **Balance** | Баланс пользователя по конкретной валюте: доступно, заблокировано, всего. Зеркало данных Bybit, обновляется через `SyncBalances`. |
| **Transaction** | Запись об операции изменения баланса: тип, сумма, валюта, связь со сделкой, timestamp. |
| **TransactionType** | Тип транзакции: `trade_buy`, `trade_sell`, `lock`, `unlock`, `fee`, `sync_adjustment`. |

**Инварианты:**
- `available + locked = total` — всегда.
- `locked` синхронизируется с `frozenQuantity` из Bybit при каждом `SyncBalances`.
- `LockFunds` / `UnlockFunds` — предварительная проверка и локальный учёт, фактическая заморозка — на стороне Bybit.
- При расхождении с Bybit — приоритет данным Bybit, логирование расхождений.
- Транзакция — append-only, не редактируется и не удаляется.

**Доменные события:**
- `BalanceSynced` — баланс синхронизирован с Bybit
- `FundsLocked` — средства заблокированы под сделку
- `FundsUnlocked` — блокировка снята
- `FundsTransferred` — средства переведены (завершение сделки)
- `BalanceDiscrepancyDetected` — расхождение с Bybit

### 2.4. Notification — Уведомления

**Ответственность:** формирование, хранение и доставка уведомлений по различным каналам.

**Ключевые понятия:**

| Понятие | Описание |
|---------|----------|
| **Notification** | Уведомление пользователя: тип, категория, заголовок, текст, статус прочтения, каналы доставки. |
| **NotificationCategory** | Категория: `trade` (торговые), `system` (системные), `security` (безопасность). |
| **NotificationChannel** | Канал доставки: `in_app`, `push`, `email`, `telegram`. |
| **NotificationPreference** | Настройки пользователя: какие категории по каким каналам получать. |

**Инварианты:**
- In-app уведомления создаются всегда, остальные каналы — по настройкам пользователя.
- Критические уведомления безопасности доставляются по всем активным каналам, игнорируя настройки.

---

### 2.5. Security — Безопасность

**Ответственность:** сессии, 2FA, мониторинг подозрительной активности, аудит.

**Ключевые понятия:**

| Понятие | Описание |
|---------|----------|
| **UserSession** | Активная сессия: устройство, IP, fingerprint, время создания, последняя активность. |
| **AuditLog** | Полный журнал действий пользователя: тип операции, сущность, IP, user-agent, payload. |
| **SecurityAlert** | Флаг подозрительной активности: тип угрозы, уровень серьёзности, статус обработки. |
| **AlertType** | Тип подозрения: `frequent_cancellations`, `large_trade`, `multiple_accounts`, `new_device_login`. |
| **TwoFactorAuth** | Настройки 2FA пользователя: метод (TOTP/SMS/Email), статус, секрет. |

**Инварианты:**
- Вход с нового устройства всегда генерирует SecurityAlert + Notification.
- При > 5 отменённых сделках за час — временная блокировка торговли.
- AuditLog — append-only, хранение 5+ лет.
- 2FA обязательна для: вывод средств, изменение API-ключей, завершение крупных сделок.

## 3. Связи между доменами

```
┌──────────────┐       ┌──────────────────┐       ┌──────────────┐
│   Identity   │──────►│     Exchange     │◄──────│    Wallet    │
│              │       │                  │       │              │
│ User         │       │ Trade            │       │ Balance      │
│ ApiConnection│       │ Advertisement    │       │ Transaction  │
└──────┬───────┘       │ OrderBookEntry   │       └──────┬───────┘
       │               └────────┬─────────┘              │
       │                        │                        │
       │               ┌───────▼──────────┐              │
       └──────────────►│  Notification    │◄─────────────┘
                       └───────┬──────────┘
                               │
                       ┌───────▼──────────┐
                       │    Security      │
                       └──────────────────┘
```

**Направление зависимостей (через контракты в `rebit.share`):**
- Exchange потребляет `BybitClientInterface`, `BybitConnectionResolverInterface`, `BalanceQueryInterface`
- Wallet потребляет `BybitClientInterface`, `BybitConnectionResolverInterface`
- Notification подписывается на события всех доменов
- Security подписывается на события Identity и Exchange
- Все модули зависят **только** от `rebit.share` — см. [modules.md](modules.md)

## 4. Внешние интеграции

### 4.1. Bybit P2P API

**Доступные операции:**

| Операция | Эндпоинт Bybit | Частота |
|----------|----------------|---------|
| Проверка API-ключей | `POST /v5/p2p/user/personal/info` | По событию |
| Получение стакана | `POST /v5/p2p/item/online` | Каждые 10 сек |
| Создание объявления | `POST /v5/p2p/item/create` | По событию |
| Обновление объявления | `POST /v5/p2p/item/update` | По событию |
| Удаление объявления | `POST /v5/p2p/item/cancel` | По событию |
| Список моих объявлений | `POST /v5/p2p/item/personal/list` | По запросу |
| Подтверждение оплаты | `POST /v5/p2p/order/pay` | По событию |
| Выпуск активов | `POST /v5/p2p/order/finish` | По событию |
| Список ордеров (all) | `POST /v5/p2p/order/simplifyList` | Каждые 10 мин |
| Активные ордера | `POST /v5/p2p/order/pending/simplifyList` | Каждые 10 сек |
| Детали ордера | `POST /v5/p2p/order/info` | По запросу |
| Информация о контрагенте | `POST /v5/p2p/user/order/personal/info` | По запросу |
| Получение балансов | `GET /v5/asset/transfer/query-account-coins-balance` | Каждые 5 мин |
| Отправка сообщения в чат | `POST /v5/p2p/order/message/send` | По событию |
| Загрузка файла для чата | `POST /v5/p2p/oss/upload_file` | По событию |

**Недоступные операции (ограничения API):**

| Операция | Решение в Rebit |
|----------|-----------------|
| Создание сделки (ордера по чужому объявлению) | Polling `order/pending/simplifyList` |
| Отмена сделки | Polling статуса; отмена на стороне Bybit |
| Открытие арбитража | Редирект в UI Bybit |
| История чата | Локальное хранение в `rebit_trade_message` |
| Платёжные методы пользователя | Извлечение из `paymentTerms` объявлений |
| Справочник платёжных методов | Локальная таблица + парсинг из ответов API |

Подробнее: [api.md § 9](api.md#9-ограничения-bybit-p2p-api).

## 5. Фоновые процессы (Background Workers)

| Процесс | Интервал | Описание |
|----------|----------|----------|
| `SyncOrderBook` | 10 сек | Polling `POST /v5/p2p/item/online` → обновление локального стакана |
| `SyncBalances` | 5 мин | Polling `GET /v5/asset/.../balance` → синхронизация балансов |
| `SyncTradeHistory` | 10 мин | Polling `POST /v5/p2p/order/simplifyList` → дозагрузка завершённых сделок |
| `SyncActiveTrades` | 10 сек | Polling `POST /v5/p2p/order/pending/simplifyList` → обнаружение новых сделок, обновление статусов (вкл. отмену по таймеру Bybit) |
| `CleanStaleOrders` | 1 мин | Удаление записей стакана старше 5 мин из локальной БД |
| `ExecuteChatScripts` | 5 сек | Отправка отложенных шагов скриптов через `POST /v5/p2p/order/message/send` |
| `MonitorSuspiciousActivity` | 5 мин | Анализ паттернов подозрительной активности |

## 6. Глоссарий

| Термин | Определение |
|--------|-------------|
| **P2P** | Peer-to-peer — прямой обмен между пользователями без центрального посредника |
| **Стакан (Order Book)** | Список активных предложений на покупку/продажу |
| **Ордер** | Предложение в стакане (может быть внешним из Bybit или собственным объявлением) |
| **Объявление (Advertisement)** | Собственный ордер пользователя, размещённый как маркет-мейкер |
| **Сделка (Trade)** | Процесс обмена между двумя сторонами по конкретному ордеру |
| **Арбитраж (Dispute)** | Процесс разрешения спора, если стороны не могут договориться |
| **Маркет-мейкер** | Пользователь, создающий собственные объявления в стакане |
| **Маркет-тейкер** | Пользователь, принимающий существующее предложение из стакана |
| **Фиат** | Фиатная валюта (RUB, USD, EUR) |
| **Токен** | Криптовалюта/стейблкоин (USDT, BTC, ETH) |
| **KYC** | Know Your Customer — процедура верификации личности |
| **Чат-скрипт (TradeChatScript)** | Заготовленный трейдером сценарий автоматических сообщений, отправляемых при открытии сделки |
| **Плейсхолдер** | Переменная в тексте шага скрипта (`{counterparty}`, `{amount}`, `{currency}`), подставляемая в момент отправки |
