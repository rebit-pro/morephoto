# Пользовательские сценарии P2P-приложения Rebit

> ⚠️ Сценарии учитывают [ограничения Bybit P2P API](api.md#9-ограничения-bybit-p2p-api).
> Операции, недоступные через API (создание сделки, отмена, арбитраж, история чата),
> реализуются через polling, локальное хранение или редирект в UI Bybit.

### **АКТОРЫ:**
1. **Гость** - неавторизованный пользователь
2. **Пользователь** - авторизованный клиент с подключенным аккаунтом Bybit
3. **Система** - фоновые процессы

---

## **СЦЕНАРИЙ 1: ПЕРВИЧНАЯ АВТОРИЗАЦИЯ И НАСТРОЙКА**

**Предусловие:** Пользователь зашел на сайт впервые.

**Основной поток:**
1. Гость нажимает "Войти"
2. Система перенаправляет на страницу входа Bitrix
3. После успешной авторизации Bitrix система проверяет наличие подключенного аккаунта Bybit
4. Если аккаунт не подключен → система показывает экран подключения API Bybit
5. Пользователь вводит:
    - API Key
    - Secret Key
    - Выбирает режим (тестовый/боевой)
6. Система:
    - Шифрует и сохраняет ключи
    - Выполняет тестовый запрос к API Bybit для проверки
    - При успехе → сохраняет подключение
    - При ошибке → показывает детали и просит проверить ключи

**Альтернативный поток 4a:**
- Пользователь пропускает подключение → ограниченный функционал (только просмотр стаканов)

---

## **СЦЕНАРИЙ 2: ПРОСМОТР СТАКАНОВ P2P**

**Предусловие:** Пользователь авторизован, находится на главной странице.

**Основной поток:**
1. Система автоматически загружает дефолтную валютную пару (USDT/RUB)
2. Пользователь видит:
    - Два стакана: Покупка (Buy) слева, Продажа (Sell) справа
    - В каждом стакане таблица с колонками:
        * Пользователь (имя/никнейм)
        * Цена (в рублях за USDT)
        * Доступно (количество USDT)
        * Лимиты (мин/макс сумма в рублях)
        * Методы оплаты (иконки)
3. Данные обновляются каждые 10 секунд

**Дополнительные возможности:**
1. **Смена валютной пары:**
    - Пользователь выбирает из списка: USDT/RUB, BTC/USDT, ETH/USDT и т.д.
    - Система перезагружает стаканы для выбранной пары

2. **Фильтрация:**
    - По методам оплаты (Тинькофф, Сбер, QIWI и др.)
    - По диапазону цен
    - По сумме (мин/макс)

3. **Сортировка:**
    - По цене (возрастание/убывание)
    - По доступному объему
    - По рейтингу контрагента

---

## **СЦЕНАРИЙ 3: ПОКУПКА ПО ПРЕДЛОЖЕНИЮ ИЗ СТАКАНА**

**Предусловие:** Пользователь просматривает стакан продаж.

> ⚠️ **Ограничение Bybit API:** эндпоинт создания сделки (ордера по чужому объявлению) **не существует**.
> Сделки создаются на стороне Bybit (через UI биржи). Rebit **обнаруживает** новые ордера через polling.

**Основной поток:**
1. Пользователь кликает на конкретное предложение в стакане продаж
2. Открывается модальное окно с деталями предложения:
    - Контрагент: имя, рейтинг, % завершенных сделок
    - Цена: фиксированная из стакана
    - Лимиты: мин/макс сумма сделки
    - Доступно: максимальный объем
    - Срок оплаты: 15 минут (стандартно)
3. Пользователь видит:
    - Итоговую сумму к получению/отправке
    - Комиссию Bybit
    - Итоговую сумму с комиссией
4. Пользователь нажимает «Перейти на Bybit для создания сделки»
5. Система:
    - Перенаправляет пользователя на Bybit (deep link с параметрами объявления)
    - Начинает polling `order/pending/simplifyList` для обнаружения нового ордера
6. После создания сделки на Bybit:
    - Агент `SyncActiveTrades` обнаруживает новый ордер
    - Создаёт локальную запись в `rebit_trade`
    - Генерирует событие `TradeDiscovered`
    - Если к объявлению привязан чат-скрипт — запускает автоскрипт
    - Пользователь видит сделку в разделе «Активные сделки»

**Альтернативный поток 4a:**
- Пользователь не создал сделку на Bybit → через N минут polling не обнаружил ордер, ничего не происходит
- Ордер уже занят → система обновляет стакан, предложение исчезает

---

## **СЦЕНАРИЙ 4: ОЖИДАНИЕ И ПОДТВЕРЖДЕНИЕ ОПЛАТЫ**

**Предусловие:** Обнаружена сделка в статусе «Ожидание оплаты» (status=10, `pending_payment`)

**Основной поток:**
1. Система показывает страницу сделки с:
    - Данными контрагента и реквизитами для оплаты (из `order/info` → `paymentTermList`)
    - Таймером обратного отсчета (из `transferLastSeconds`)
    - Кнопкой «Я оплатил»
    - Чат с контрагентом (отправка через Bybit API, история — локальная)
2. Система автоматически:
    - Отправляет системное сообщение «Сделка создана» в чат (через `order/message/send`)
    - Если к объявлению привязан чат-скрипт → последовательно отправляет шаги скрипта от имени трейдера (с учётом задержек)
3. Пользователь общается с контрагентом в чате: уточняет реквизиты, согласовывает детали
4. Пользователь совершает перевод по реквизитам
5. Пользователь нажимает «Я оплатил»
6. Система:
    - Вызывает `POST /v5/p2p/order/pay` с выбранным платёжным методом
    - Обновляет локальный статус на `payment_sent` (status=20)
    - Отправляет системное сообщение в чат «Покупатель отметил оплату»
7. Контрагент подтверждает получение оплаты (на Bybit или в Rebit)
8. Если продавец в Rebit → система вызывает `POST /v5/p2p/order/finish`
9. Система:
    - Обнаруживает через polling завершение сделки (status=50)
    - Обновляет балансы через `SyncBalances`
    - Отправляет системное сообщение «Сделка завершена»
    - Чат переходит в режим «только чтение»
    - Добавляет запись в историю

**Альтернативный поток 3a:**
- Таймер истек → Bybit автоматически отменяет сделку; Rebit обнаруживает status=40 через polling
- Контрагент не подтвердил оплату → пользователь **перенаправляется в UI Bybit** для открытия арбитража (нет API для этого)
- Пользователь хочет отменить → **перенаправляется в UI Bybit** (нет API для отмены)

---

## **СЦЕНАРИЙ 5: ПРОСМОТР ЛИЧНОГО КАБИНЕТА**

**Основной поток:**
1. Пользователь переходит в "Мой кабинет"
2. **Вкладка "Балансы":**
    - Таблица с валютами: доступно, заблокировано (Bybit `frozenQuantity`), всего
    - Кнопка «Синхронизировать» — ручной вызов `SyncBalances`
    - Время последней синхронизации
3. **Вкладка "Активные сделки":**
    - Текущие сделки с фильтрами: все, покупка, продажа
    - Детальный просмотр каждой сделки
    - Ссылка «Перейти на Bybit» для операций, недоступных через API (отмена, арбитраж)
4. **Вкладка "История сделок":**
    - Таблица завершенных сделок с пагинацией
    - Фильтры: дата, тип, валюта, статус
    - Экспорт в CSV
5. **Вкладка "Статистика":**
    - Оборот за периоды (день, неделя, месяц, год)
    - Прибыль/убыток (в рублях и в процентах)
    - Количество сделок
    - Графики: оборот по дням, распределение по валютам
    - Сравнение с предыдущим периодом

---

## **СЦЕНАРИЙ 6: СОЗДАНИЕ СОБСТВЕННОГО ОРДЕРА (МАРКЕТ-МЕЙКЕР)**

**Предусловие:** Пользователь хочет выставить свое предложение

**Основной поток:**
1. Пользователь нажимает "Создать объявление"
2. Выбирает тип: Продать / Купить
3. Выбирает валютную пару
4. Заполняет параметры:
    - Цена (фиксированная или плавающая)
    - Доступное количество
    - Лимиты сделки (мин/макс сумма)
    - Выбор платежных методов (один или несколько)
    - Условия сделки (комментарий)
    - **Скрипт автосообщений** (опционально): выбор из сохранённых скриптов или «Без скрипта»
5. Система показывает предварительный расчет и комиссию
6. Пользователь подтверждает
7. Система:
    - Вызывает `POST /v5/p2p/item/create` в Bybit API
    - При успехе → Bybit замораживает указанный объём (`frozenQuantity`)
    - Создаёт локальную запись объявления
    - Синхронизирует баланс (`SyncBalances`) для отражения заморозки
    - Уведомляет при появлении покупателей/продавцов (через polling)

---

## **СЦЕНАРИЙ 7: ФОНОВЫЕ ПРОЦЕССЫ СИНХРОНИЗАЦИИ**

**Процесс 7.1: Синхронизация стаканов**
- Каждые 10 секунд: polling `POST /v5/p2p/item/online`
- Обновление локальной БД (`rebit_order_book`)
- Отправка push-уведомлений подключенным клиентам об изменениях
- Очистка устаревших ордеров (старше 5 минут)

**Процесс 7.2: Синхронизация балансов**
- При входе пользователя
- После обнаружения завершённой сделки
- Раз в 5 минут для активных пользователей
- Polling `GET /v5/asset/transfer/query-account-coins-balance`
- Обновление `rebit_balance` (вкл. `locked` из Bybit `frozenQuantity`)

**Процесс 7.3: Синхронизация истории сделок**
- При первом подключении аккаунта: загрузка истории через `POST /v5/p2p/order/simplifyList`
- Затем каждые 10 минут: дозагрузка завершённых сделок

**Процесс 7.4: Синхронизация активных сделок**
- Каждые 10 секунд: polling `POST /v5/p2p/order/pending/simplifyList`
- Обнаружение новых ордеров → создание локальных записей, запуск чат-скриптов
- Обнаружение смены статусов → обновление локальных данных (вкл. отмену по таймеру Bybit)
- Уведомление пользователей при изменении статуса сделки

- При подозрении → временная блокировка и запрос верификации

**8.3: Сессии и устройства**
- Просмотр активных сессий
- Возможность завершить все сессии
- Уведомления о входе с нового устройства

## **СЦЕНАРИЙ 11: ОБЩЕНИЕ В ЧАТЕ СДЕЛКИ**

**Предусловие:** Сделка обнаружена и находится в активном статусе (`pending_payment`, `payment_sent`, `payment_confirmed` или `disputed`).

> ⚠️ **Ограничение Bybit API:** эндпоинт для чтения истории чата **не существует**.
> История хранится **только в локальной БД** (`rebit_trade_message`).
> Сообщения контрагента, отправленные через UI Bybit, **не будут видны** в Rebit.

**Основной поток:**
1. При открытии страницы сделки система загружает историю сообщений из локальной БД
2. Пользователь видит панель чата с:
    - Историей отправленных и системных сообщений (из `rebit_trade_message`)
    - Полем ввода текста
    - Кнопкой прикрепления файла (изображение/PDF/видео)
3. Пользователь вводит сообщение и нажимает «Отправить»
4. Система:
    - Вызывает `POST /v5/p2p/order/message/send` для доставки через Bybit
    - Сохраняет сообщение в локальную БД (`rebit_trade_message`) с типом `user`
    - Отображает сообщение в чате
5. Для отправки файла:
    - Система загружает файл через `POST /v5/p2p/oss/upload_file` → получает URL
    - Отправляет сообщение с URL через `order/message/send` с `contentType` = `pic`/`pdf`/`video`

**Системные сообщения (автоматические):**
- Система отправляет сообщения с типом `system` через `order/message/send` при каждой смене статуса:
    - «Сделка создана. Ожидается оплата.»
    - «Покупатель отметил оплату.»
    - «Продавец подтвердил получение средств.»
    - «Сделка завершена.» / «Сделка отменена.»
    - «Внимание: до истечения срока оплаты осталось 5 минут.»
- Все системные сообщения дублируются в `rebit_trade_message`

**Автосообщения из скрипта:**
- Если к объявлению привязан чат-скрипт, при обнаружении новой сделки система:
    1. Берёт шаги скрипта, отсортированные по `sort`
    2. Подставляет плейсхолдеры: `{counterparty}` → имя контрагента, `{amount}` → сумма, `{currency}` → валюта
    3. Отправляет каждый шаг через `POST /v5/p2p/order/message/send` от имени владельца скрипта с заданной задержкой (`delay_seconds`)
    4. Сообщения сохраняются в `rebit_trade_message` с типом `script` для визуального отличия в UI

**Режим «только чтение»:**
- При переходе сделки в `completed` или `cancelled`:
    - Поле ввода блокируется
    - Вся история остаётся доступна для просмотра
    - Отображается баннер «Сделка завершена / отменена. Чат закрыт.»

**Альтернативные потоки:**
- Ошибка отправки через Bybit API → повторная попытка с уведомлением пользователя
- Спам (> 10 сообщений за 30 секунд) → временная блокировка отправки на 60 секунд
- Сообщения контрагента через UI Bybit → **не** отображаются в Rebit (нет API для чтения)

## **СЦЕНАРИЙ 12: УПРАВЛЕНИЕ СКРИПТАМИ АВТОСООБЩЕНИЙ**

**Предусловие:** Пользователь авторизован, находится в разделе «Настройки» → «Скрипты чата».

### **12.1: Просмотр списка скриптов**
1. Пользователь видит таблицу своих скриптов:
    - Название
    - Количество шагов
    - Статус (активен / неактивен)
    - Используется в N объявлениях
    - Дата создания
2. Доступны действия: создать, редактировать, копировать, удалить

### **12.2: Создание скрипта**
1. Пользователь нажимает «Создать скрипт»
2. Вводит название (например: «Приветствие + реквизиты Сбер»)
3. Добавляет шаги по порядку:
    - **Шаг 1:** Текст сообщения, задержка 0 сек
      > «Здравствуйте, {counterparty}! Спасибо за выбор моего предложения.»
    - **Шаг 2:** Текст сообщения, задержка 3 сек
      > «Переведите {amount} {currency} на карту Сбербанка: 4276 **** **** 1234, получатель: Иванов И.И.»
    - **Шаг 3:** Текст сообщения, задержка 5 сек
      > «После оплаты нажмите кнопку "Я оплатил". Если возникнут вопросы — пишите в чат.»
4. Для каждого шага можно:
    - Редактировать текст
    - Задать задержку (0–300 секунд)
    - Изменить порядок (drag & drop)
    - Удалить шаг
5. Пользователь видит предпросмотр: как будет выглядеть скрипт в чате
6. Нажимает «Сохранить»

**Доступные плейсхолдеры:**
| Плейсхолдер | Подставляется |
|-------------|---------------|
| `{counterparty}` | Имя/никнейм контрагента |
| `{amount}` | Сумма сделки |
| `{currency}` | Код валюты (USDT, BTC) |
| `{fiat_amount}` | Сумма в фиате |
| `{fiat_currency}` | Фиатная валюта (RUB, USD) |
| `{trade_id}` | Номер сделки |

### **12.3: Привязка скрипта к объявлению**
1. При создании/редактировании объявления (Сценарий 6) пользователь выбирает скрипт из выпадающего списка
2. Один скрипт может быть привязан к нескольким объявлениям
3. При обнаружении новой сделки по объявлению — система автоматически запускает привязанный скрипт
4. При откреплении/удалении скрипта — уже запущенные сделки не затрагиваются

### **12.4: Удаление скрипта**
1. Пользователь нажимает «Удалить»
2. Если скрипт привязан к активным объявлениям → система предупреждает и предлагает:
    - Отвязать скрипт от объявлений и удалить
    - Отмена
3. При удалении — связь `UF_CHAT_SCRIPT_ID` в объявлениях обнуляется

## **КРОСС-ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ:**

1. **Производительность:**
    - Загрузка стакана < 2 секунд
