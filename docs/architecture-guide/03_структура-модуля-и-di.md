# Структура модуля и DI

Эта глава объясняет, как должен быть устроен модуль физически и как в нём собираются зависимости.
Структура модуля в проекте не случайна: она отражает архитектуру.

Если структура расползается, быстро появляются типовые проблемы:

- код начинает мигрировать между слоями без правил;
- `ServiceLocator` появляется в бизнес-логике;
- модули становятся непредсказуемыми для команды.

## 1. Общая структура модуля

Целевая структура:

```text
api/public/local/modules/rebit.<name>/
  di/
    Layers/
    <Domain>.php
  events/
    events.php
  install/
    components/
    index.php
  lib/
    Application/
    Domain/
    Infrastructure/
    Presentation/
    Shared/
  include.php        # проверка зависимых модулей и подключение events
  routes.php          # если есть API
  .settings.php       # точка входа Bitrix для DI, подключает файлы из di/
```

## 2. Что означает каждая папка и файл

| Путь | Что означает                                                                                                         | Почему нужен |
|---|----------------------------------------------------------------------------------------------------------------------|---|
| `di/` | конфигурация контейнера                                                                                              | чтобы зависимости собирались централизованно |
| `di/Layers/` | регистрации по техническим срезам                                                                                    | чтобы не сваливать всё в один файл |
| `di/<Domain>.php` | регистрации по предметным зонам                                                                                      | чтобы доменные сценарии были сгруппированы |
| `events/` | регистрация Bitrix-событий модуля                                                                                    | чтобы не держать регистрацию событий прямо в `include.php` |
| `install/` | установка и удаление модуля                                                                                          | Bitrix требует это как точку входа (entrypoint) |
| `install/components/` | компоненты модуля. Внутри не должно быть шаблонов! Все шаблоны в `/local/templates/`                                 | чтобы компонент поставлялся вместе с модулем |
| `lib/Application` | сценарии (use case), DTO, порты, прикладные сервисы (app service)                                                    | здесь живёт сценарий приложения |
| `lib/Domain` | предметная модель и репозитории                                                                                      | здесь живёт предметная логика |
| `lib/Infrastructure` | интеграции, адаптеры, legacy                                                                                         | здесь живут внешние детали |
| `lib/Presentation` | component builder (сборщик компонента), controller (контроллер), command (команда), view model (модель представления) | вход и выход системы |
| `lib/Shared` | общее только для этого модуля                                                                                        | чтобы не размазывать мелкие общие вещи |
| `include.php` | bootstrap модуля: проверка зависимых модулей и подключение `events/events.php`                                       | чтобы точка входа модуля оставалась тонкой |
| `routes.php` | описание HTTP-маршрутов                                                                                              | только если есть API |
| `.settings.php` | точка входа Bitrix для DI-конфигурации модуля                                                                        | обычно собирает `services` через `require` файлов из `di/` |

## 3. Минимальный набор для нового модуля

Не каждому модулю нужен весь набор файлов.

### Обязательно

- `install/index.php`
- `include.php`
- `di/`
- `lib/` со слоями

### Опционально

- `install/components/`, если модуль поставляет компоненты;
- `routes.php`, если модуль даёт HTTP API;
- `.settings.php`, чтобы Bitrix увидел DI-конфигурацию модуля.

## 4. Пример жизненного цикла модуля

```text
Установка модуля
  -> install/index.php
  -> RegisterModule(...)
  -> установка компонентов
  -> при необходимости регистрация маршрутов

Подключение модуля
  -> include.php
  -> проверка зависимостей
  -> регистрация событий
  -> bootstrap (начальная инициализация)
```

## 5. `install/index.php`

### Что это

Точка входа Bitrix (entrypoint) для установки и удаления модуля.

### Что он должен делать

- регистрировать модуль;
- устанавливать компоненты;
- удалять модуль и компоненты;
- при необходимости работать с маршрутами.

### Чего там не должно быть

- предметной логики;
- orchestration use case (оркестрации сценариев);
- случайных интеграций;
- runtime-решений, не относящихся к установке.

### Пример

```php
final class Rebit_Example extends CModule
{
    use ModuleComponentInstallerTrait;

    public $MODULE_ID = 'rebit.example';
    public $MODULE_VERSION = '1.0.0';
    public $MODULE_VERSION_DATE = '2026-01-01 00:00:00';
    public $MODULE_NAME = 'rebit.example';
    public $MODULE_DESCRIPTION = 'Пример нового модуля';

    public function __construct()
    {
        $this->initModuleComponentInstaller();
    }

    public function DoInstall(): bool
    {
        RegisterModule($this->MODULE_ID);
        $this->installComponents();

        return true;
    }

    public function DoUninstall(): bool
    {
        UnRegisterModule($this->MODULE_ID);
        $this->uninstallComponents();

        return true;
    }
}
```

## 6. `include.php`

### Что это

Bootstrap-слой (начальная инициализация) модуля.

### Что он должен делать

- проверять, что обязательные модули подключены;
- подключать `events/events.php`.

### Что он не должен делать

- содержать тяжёлую бизнес-логику;
- становиться «скрытым слоем выполнения (runtime) приложения».

### Пример

```php
ModuleHelper::validateModuleInstalled('rebit.share');

include_once __DIR__ . '/events/events.php';
```

Для событий Битрикс мы используем тонкий мост в нашу архитектуру:

- `include.php` или `events/events.php` только регистрирует callback.
- мост получает обработчик через `AbstractEventBridge`.
- реальная логика живёт в обработчике в `Infrastructure`.

Подробно этот паттерн описан в [14. Bitrix-события и тонкий мост](14_bitrix-события.md).

## 7. Что такое DI в проекте

### Простое объяснение

DI нужен, чтобы класс не создавал свои зависимости сам.
Он просто говорит:

«Мне нужен вот такой объект».

А контейнер решает, какой именно экземпляр дать.

### Зачем это нужно

Без DI классы начинают:

- тащить `ServiceLocator` везде;
- создавать зависимости вручную;
- скрывать реальный граф вызовов;
- смешивать оркестрацию (orchestration) и сборку инфраструктуры.

## 8. Как устроен DI в проекте

DI-конфиги лежат в `di/`.
Сервисы живут как одиночки (singleton) в рамках запроса или CLI-процесса.

Но для самого Bitrix входной точкой остаётся `.settings.php` модуля.
То есть правило в проекте такое:

- регистрации сервисов пишем в `di/`;
- `.settings.php` подключает файлы из `di/`;
- Bitrix регистрирует `services` уже из `.settings.php`.

Отсюда важное правило: сервис не должен хранить изменяемое состояние между вызовами внутри одного запроса.

### Почему

Если сервис-одиночка (singleton) хранит меняющееся состояние, поведение становится неявным и начинает зависеть от порядка вызовов.

### Как это выглядит в реальном модуле

Эталонный пример: [api/public/local/modules/rebit.wallet/.settings.php](api/public/local/modules/rebit.wallet/.settings.php)

```php
return [
    'services' => [
        'value' => array_merge(
            require __DIR__ . '/di/Facet.php',
            require __DIR__ . '/di/SmartFilter.php',
            require __DIR__ . '/di/Banner.php',
            require __DIR__ . '/di/Seo.php',
            require __DIR__ . '/di/Product.php',
            require __DIR__ . '/di/Wishlist.php',
            require __DIR__ . '/di/Layers/Presentation.php',
            require __DIR__ . '/di/Layers/Infrastructure.php',
            require __DIR__ . '/di/Layers/Shared.php',
        ),
    ],
];
```

То есть реальные DI-регистрации живут в `di/`, а `.settings.php` только собирает их в один массив для Bitrix.

## 9. Пример DI-регистрации

```php
return [
    GetFooUseCase::class => [
        'className' => GetFooUseCase::class,
        'constructorParams' => static function(): array {
            $locator = ServiceLocator::getInstance();

            return [
                $locator->get(FooGatewayInterface::class),
                $locator->get(FooAppService::class),
            ];
        },
    ],
    FooGatewayInterface::class => [
        'constructor' => static function(): FooGatewayInterface {
            return new ElasticFooGateway(
                ServiceLocator::getInstance()->get(ElasticClientFactory::class)->create(),
            );
        },
    ],
    FooAppService::class => [
        'className' => FooAppService::class,
    ],
];
```

### Важное ограничение Bitrix DI

Для ключа-интерфейса запись с `className` работает как alias до concrete-класса.
Если такой concrete-класс требует ручной сборки зависимостей, Bitrix попытается собрать его автопроводкой и проигнорирует `constructorParams`, привязанные к интерфейсному ключу.

Поэтому правило такое:

- если реализация порта собирается автопроводкой без специальных аргументов, можно писать `Interface::class => ['className' => Concrete::class]`;
- если реализации нужны scalar-аргументы, клиент из factory или другой неавтособираемый объект, нужно писать `Interface::class => ['constructor' => static function() { return new Concrete(...); }]`.

### Как выбирать ключ DI-регистрации

Правило простое:

- если класс зависит от порта или межмодульного контракта, ключ DI должен быть интерфейсом;
- если это внутренний сервис без архитектурной границы, ключ DI может быть concrete-классом.

Хорошо:

```php
FooGatewayInterface::class => [
    'className' => ElasticFooGateway::class,
]
```

Тоже хорошо, если нужна ручная сборка:

```php
FooGatewayInterface::class => [
    'constructor' => static function(): FooGatewayInterface {
        return new ElasticFooGateway(
            ServiceLocator::getInstance()->get(ElasticClientFactory::class)->create(),
        );
    },
]
```

Тоже хорошо:

```php
FooAppService::class => [
    'className' => FooAppService::class,
]
```

## 10. Почему `ServiceLocator` разрешён только в отдельных местах

`ServiceLocator` скрывает зависимости.
Поэтому он допустим только там, где идёт именно сборка графа зависимостей, а не выполнение предметной логики.

### Допустимо

- DI-конфиги;
- legacy-код, `include.php`, bootstrap и тонкий integration bridge для событий Bitrix.

## 11. Как делить DI-файлы

Хорошая практика:

- `di/Layers/Infrastructure.php`
- `di/Layers/Presentation.php`
- `di/Layers/Shared.php`
- отдельные доменные DI-файлы: `Facet.php`, `Seo.php`, `Product.php`, `SmartFilter.php`

### Почему так лучше

Потому что один гигантский DI-файл быстро становится нечитаемым.
А доменная разбивка облегчает:

- навигацию;
- ревью;
- локальные изменения;
- поиск зависимостей.

## 12. Что показывает `rebit.wallet`

`rebit.wallet` подтверждает основную схему:

- есть `di/` с разбивкой по доменам и слоям;
- есть `install/components`;
- есть `lib/Application`, `lib/Domain`, `lib/Infrastructure`, `lib/Presentation`, `lib/Shared`;
- есть `include.php`.

## 13. Чего нельзя делать

- регистрировать зависимости прямо в бизнес-коде;
- тащить `ServiceLocator` в `UseCase`;
- держать изменяемое состояние в singleton-сервисах;

## 14. Что нужно запомнить

1. Структура модуля должна выражать архитектуру.
2. `di/` это место сборки зависимостей, а не место бизнес-логики.
3. `include.php` это bootstrap (начальная инициализация).
4. `ServiceLocator` допустим только на границах сборки и интеграции.
5. Не каждый модуль обязан иметь API-слой.
