# Кросс-доменное взаимодействие

Эта глава объясняет, как домены внутри одного модуля и между модулями обмениваются данными.

Если не договориться о правилах, быстро появляются проблемы:

- UseCase одного домена напрямую вызывает UseCase другого и получает двойное кэширование;
- ошибки одного домена незаметно гасятся внутри другого;
- при изменении одного домена ломается чужой сценарий;
- граф зависимостей превращается в клубок.

## Три уровня взаимодействия

| Уровень | Механизм | Пример |
|---|---|---|
| Внутри одного домена | UseCase вызывает UseCase напрямую через DI | SmartFilter: `GetSmartFilterValueDictionaryUseCase` → `CreateSmartFilterDictionaryUseCase` |
| Между доменами одного модуля | UseCase → Outgoing Port → Infrastructure Adapter | SmartFilter → Facet: `CreateSmartFilterDictionaryUseCase` → `SmartFilterFacetValueQueryInterface` → `SmartFilterFacetValueQueryAdapter` |
| Между модулями | UseCase → Contract из `rebit.share` → Adapter в модуле-поставщике | Bybit → Identity: `SyncBalanceUseCase` → `ApiConnectionQueryInterface` → `ApiConnectionQueryAdapter` |

## Главное правило: запрещён UseCase → UseCase между доменами

UseCase это сценарий с оркестрацией: кэш, логирование, обработка ошибок, fallback-стратегии.
Прямой вызов чужого UseCase создаёт вложенную оркестрацию и приводит к проблемам:

- **Двойное кэширование** — внешний и внутренний UseCase кэшируют независимо, инвалидация непредсказуема.
- **Непрозрачные ошибки** — внутренний UseCase подавляет исключение и возвращает fallback, внешний не знает об этом.
- **Лишние зависимости** — нужны только данные, а тянется вся цепочка оркестрации.
- **Сложность тестирования** — для проверки одного домена нужно поднимать всю инфраструктуру другого.

## Внутри одного домена: UseCase → UseCase допустим

Внутри домена UseCase может вызывать другой UseCase как подшаг:

```php
// SmartFilter домен — оба UseCase в одном домене
final readonly class GetSmartFilterValueDictionaryUseCase
{
    public function __construct(
        private CreateSmartFilterDictionaryUseCase $createSmartFilterDictionaryUseCase,
    ) {}

    public function execute(array $sectionIds): array
    {
        if ($this->isDictionaryEmpty($sectionIds)) {
            $this->createSmartFilterDictionaryUseCase->execute();
        }

        // ...
    }
}
```

Это допустимо, потому что:

- оба UseCase разделяют один контекст ошибок и кэширования;
- нет пересечения границ ответственности;
- при изменении одного UseCase второй адаптируется в рамках того же домена.

## Между доменами одного модуля: Outgoing Port + Adapter

Если домену SmartFilter нужны данные из Facet, это запрос данных, а не вызов сценария.
Запрос данных оформляется через Outgoing Port в домене-потребителе.

### Шаг 1. Порт в домене-потребителе

```php
// Application/SmartFilter/Port/Outgoing/SmartFilterFacetValueQueryInterface.php
interface SmartFilterFacetValueQueryInterface
{
    /**
     * @param int[] $propertyIds
     *
     * @return array<int, FacetSectionValuesDto> ключ — ID раздела
     */
    public function getPropertyValuesBySection(array $propertyIds): array;
}
```

### Шаг 2. Adapter в Infrastructure

Адаптер делегирует в инфраструктурную реализацию домена-поставщика **напрямую**, минуя его UseCase:

```php
// Infrastructure/SmartFilter/Adapter/SmartFilterFacetValueQueryAdapter.php
final readonly class SmartFilterFacetValueQueryAdapter implements SmartFilterFacetValueQueryInterface
{
    public function __construct(
        private FacetValueArrayQueryInterface $facetValueArrayQuery,
    ) {}

    public function getPropertyValuesBySection(array $propertyIds): array
    {
        if ([] === $propertyIds) {
            return [];
        }

        return $this->facetValueArrayQuery->getPropertyValuesBySection($propertyIds);
    }
}
```

### Шаг 3. DI-связывание

В DI домена-потребителя связывается интерфейс порта с адаптером:

```php
// di/SmartFilter.php
FacetValueArrayQueryInterface::class => [
    'constructor' => static function(): FacetValueArrayQueryInterface {
        return new ElasticFacetValueArrayQuery(
            ServiceLocator::getInstance()->get(ElasticClientFactory::class)->create(),
            ServiceLocator::getInstance()->get(ElasticFacetIndexNameResolver::class),
        );
    },
],
SmartFilterFacetValueQueryInterface::class => [
    'constructor' => static function(): SmartFilterFacetValueQueryInterface {
        return new SmartFilterFacetValueQueryAdapter(
            ServiceLocator::getInstance()->get(FacetValueArrayQueryInterface::class),
        );
    },
],
```

UseCase получает порт, а не конкретный адаптер:

```php
CreateSmartFilterDictionaryUseCase::class => [
    'className' => CreateSmartFilterDictionaryUseCase::class,
    'constructorParams' => static function(): array {
        $locator = ServiceLocator::getInstance();

        return [
            // ...
            $locator->get(SmartFilterFacetValueQueryInterface::class),
            // ...
        ];
    },
],
```

Это важное правило:

- `UseCase` зависит от порта;
- DI связывает порт с адаптером;
- concrete-класс адаптера остаётся деталью инфраструктуры.

Отдельно важно помнить ограничение Bitrix DI:

- для interface-key запись `className + constructorParams` не подходит, если адаптер собирается вручную;
- в таких случаях нужно использовать `constructor` и возвращать готовый adapter;
- `className` для interface-key оставляем только там, где concrete-класс безопасно собирается автопроводкой.

### Обратная связь: Facet → SmartFilter

Связь работает в обе стороны. Facet тоже может запрашивать данные у SmartFilter:

```php
// Application/Facet/Port/Outgoing/FacetSmartFilterConfigQueryInterface.php
interface FacetSmartFilterConfigQueryInterface
{
    /**
     * @param int[] $sectionIds если пустой массив, то для всех разделов
     *
     * @return array<int, SmartFilterAdminConfigDto> ключ — ID раздела
     */
    public function getPropertiesConfig(array $sectionIds = []): array;
}
```

```php
// Infrastructure/Facet/Adapter/FacetSmartFilterConfigQueryAdapter.php
final readonly class FacetSmartFilterConfigQueryAdapter implements FacetSmartFilterConfigQueryInterface
{
    public function __construct(
        private SmartFilterConfigProvider $configProvider,
    ) {}

    public function getPropertiesConfig(array $sectionIds = []): array
    {
        $configs = $this->configProvider->getSmartFilterPropertiesConfig(0);

        if ([] === $sectionIds) {
            return $configs;
        }

        $keys = array_fill_keys($sectionIds, true);

        return array_intersect_key($configs, $keys);
    }
}
```

Здесь адаптер делегирует в `SmartFilterConfigProvider` (Application Service), минуя `GetSmartFilterPropertiesConfigUseCase` (который добавляет кэш).

### Почему адаптер обходит UseCase поставщика

UseCase содержит оркестрацию: кэширование, логирование, fallback.
Адаптер должен обращаться к нижнему уровню:

- к Outgoing Port интерфейсу другого домена (инфраструктурная реализация);
- или к Application Service (который не является сценарием и не содержит собственной оркестрации).

Это исключает двойное кэширование и непрозрачные ошибки.

## Между модулями: Contract в `rebit.share`

Если домен из одного модуля должен получить данные из другого модуля, контракт выносится в `rebit.share/lib/Contracts/`:

```text
rebit.share/lib/Contracts/Medical/
    ListSalonsPortInterface.php
    Dto/Input/ListSalonsInputDto.php
    Dto/Output/SalonsListOutputDto.php
```

Модуль-поставщик (`rebit.identity`) реализует контракт через Adapter в `Infrastructure/Adapter/`.
Модуль-потребитель (`rebit.bybit`) зависит только от интерфейса из `rebit.share`.

Пример контракта: `rebit.share/lib/Application/Contract/Bybit/` — DTO подключения к Bybit API.

Сама регистрация живёт в DI-файле модуля-поставщика.
Дальше этот DI-файл подключается из `.settings.php` модуля, как это сделано в `rebit.wallet`.

```php
ListSalonsPortInterface::class => [
    'className' => ListSalonsAdapter::class,
],
```

Для межмодульных контрактов ключ DI должен быть интерфейсом контракта.
Именно так контейнер явно показывает границу между модулями.

## Incoming Port: не используется

В проекте было принято решение не использовать явные интерфейсы Incoming Port (вроде `GetSmartFilterValueDictionaryPortInterface`).

Вместо этого:

- UseCase вызывается напрямую через DI;
- контракт входа/выхода определяется `InputDto` / `OutputDto`;
- папка `Port/Incoming/` не создаётся.

Это упрощает код, но требует дисциплины: DTO должны быть immutable и well-typed (`final readonly`).

## Куда размещать DTO

| Слой | Размещение |
|---|---|
| Входные/выходные DTO UseCase | `Application/<Domain>/Dto/` |
| DTO портов | `Application/<Domain>/Port/Outgoing/Dto/` или `Application/<Domain>/Port/Dto/` |
| DTO компонентов | `Presentation/Component/<Name>/Dto/` |
| Межмодульные DTO | `rebit.share/lib/Contracts/<Domain>/Dto/Input/` и `Dto/Output/` |

## Чеклист

- UseCase зависит только от портов своего домена или UseCase своего домена.
- Кросс-доменные данные запрашиваются через Outgoing Port + Adapter.
- Adapter делегирует в инфраструктуру или AppService напрямую, не в чужой UseCase.
- Кросс-модульные зависимости идут через Contract в `rebit.share`.
- В DI порты и межмодульные контракты регистрируются по интерфейсу.

## Что нужно запомнить

1. Между доменами UseCase не вызывает UseCase напрямую.
2. Связь между доменами идёт через Outgoing Port в домене-потребителе + Adapter в Infrastructure.
3. Adapter обходит UseCase поставщика и обращается к его инфраструктуре или AppService.
4. Между модулями контракт выносится в `rebit.share`.
5. В DI порт связывается с адаптером через интерфейс, а Incoming Port как интерфейс не используется.
