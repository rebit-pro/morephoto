# Очереди и консьюмеры

Эта глава объясняет, как в проекте устроена асинхронная обработка через очереди сообщений.

## 1. Зачем нужны очереди

Некоторые операции слишком тяжёлые или медленные, чтобы выполнять их прямо в текущем процессе.
Например: обновление поискового индекса, отправка email, пересчёт агрегатов.

Вместо того чтобы делать это синхронно, мы **отправляем сообщение в очередь**.
Отдельный процесс — **консьюмер** — забирает сообщение и обрабатывает его в фоне.

```
Любой код (UseCase, Controller, Event Handler, CLI-команда)
    → Publisher отправляет сообщение в очередь
        → Консьюмер забирает сообщение
            → Message Handler выполняет работу
```

Отправитель не знает, когда и как сообщение будет обработано. Он просто кладёт задание и продолжает работу.

## 2. Стек

| Что | Чем реализовано |
|---|---|
| Брокер сообщений | RabbitMQ (AMQP) |
| Библиотека | Symfony Messenger |
| Транспорт | `AmqpTransport` (Symfony Messenger Bridge) |
| Сериализация | `PhpSerializer` (нативная PHP-сериализация) |

Symfony Framework не используется. Bus собирается вручную через наши фабрики.

## 3. Ключевые понятия

### Сообщение (Message)

Обычный PHP-объект с данными. Описывает **что нужно сделать**.
Все сообщения наследуются от `AbstractMessage`.

```php
final readonly class FacetUpdateMessage extends AbstractMessage
{
    public function __construct(
        public int $productId,
        public FacetUpdateSourceEnum $source,
    ) {
        parent::__construct();
    }

    public function getDeduplicationKey(): string
    {
        return 'facet_update_' . $this->productId;
    }
}
```

Что даёт `AbstractMessage`:
- автоматически ставит `$createdAt` (время создания);
- даёт дефолтный `getDeduplicationKey()` через md5 от payload.

Сообщение живёт в **Application**: `lib/Application/<Domain>/Message/<Name>Message.php`.

### Обработчик сообщения (Message Handler)

Класс с методом `__invoke()`, который принимает сообщение и делает полезную работу.
Вызывается консьюмером, когда тот достаёт сообщение из очереди.

```php
final readonly class FacetUpdateMessageHandler
{
    public function __construct(
        private FacetAppService $facetAppService,
        private FacetIndexerInterface $facetIndexer,
        private FacetDocumentQueryInterface $facetDocumentQuery,
        private LoggerInterface $logger,
    ) {}

    public function __invoke(FacetUpdateMessage $message): void
    {
        // обновить индекс для товара $message->productId
    }
}
```

Handler живёт рядом с сообщением в подпапке `Handler/`:
`lib/Application/<Domain>/Message/Handler/<Name>MessageHandler.php`.

### Publisher

Сервис, который отправляет сообщение в очередь. Реализует `MessagePublisherInterface`.

```php
$this->publisher->dispatch(
    new FacetUpdateMessage(productId: 42, source: FacetUpdateSourceEnum::PRICE_UPDATE),
    deduplicateTime: 55,
);
```

Параметры `dispatch()`:

| Параметр | Что делает |
|---|---|
| `$message` | Само сообщение (наследник `AbstractMessage`) |
| `$deduplicateTime` | Окно дедупликации в секундах (по умолчанию 0 — без дедупликации) |

Publisher можно использовать из Application и Infrastructure.
Главное — получить `MessagePublisherInterface` через DI.

### Фабрика маршрутов (Messenger Factory)

Описывает, какое сообщение каким handler'ом обрабатывается и в какую очередь уходит.
У каждого домена своя фабрика, которая наследуется от общей `AbstractMessengerFactory`:

```php
final class FacetMessengerFactory extends AbstractMessengerFactory
{
    protected static function routes(): array
    {
        return [
            new MessengerRouteDto(
                messageClass: FacetUpdateMessage::class,
                handlerClass: FacetUpdateMessageHandler::class,
                queue: MessengerQueueEnum::FACET_UPDATE,
            ),
        ];
    }
}
```

Фабрика сама не отправляет и не обрабатывает сообщения. Она **конфигурирует** bus и publisher:
- `FacetMessengerFactory::createBus($locator)` — для консьюмера;
- `FacetMessengerFactory::createPublisher($locator)` — для отправителя.

### Консьюмер (Consumer)

CLI-процесс, который слушает очередь и вызывает handler для каждого полученного сообщения.
Запускается как CLI-команда (`extends RebitCommand`), работает в цикле до исчерпания лимита сообщений или времени.

Защита от параллельного запуска — на уровне команды через атрибут `#[WithLock]` (см. [CLI-команды](10_cli-команды.md)).
`ConsumerRunner` не содержит логику блокировки — он только запускает worker.

## 4. Как устроена дедупликация

Когда одно и то же действие вызывается много раз подряд (массовый импорт, каскадные обновления),
нет смысла обрабатывать каждое событие отдельно. Дедупликация гарантирует,
что за одно окно времени в очередь уйдёт **ровно одно сообщение** с одинаковым ключом.

Логика работы (окно = `deduplicateTime`, например 55 секунд):

```
Вызов 1  →  сообщение отправлено
Вызов 2+ →  сброшено (drop), пока не истечёт окно дедупликации
```

Сообщения не несут данные — только идентификатор (например, `productId`).
Хендлер при обработке сам читает актуальное состояние из БД,
поэтому достаточно одного сообщения на окно.

Ключ дедупликации определяется методом `getDeduplicationKey()` сообщения.
Например, `FacetUpdateMessage` использует `productId` — дедупликация работает на товар.
Кеш дедупликации реализован через Bitrix ManagedCache.

Если дедупликация не нужна — просто не передавайте `deduplicateTime` (или передайте 0).

## 5. Общая схема

```
Отправка (producer):

  Любой код → Publisher->dispatch(message) → MessageBus → AMQP Transport → RabbitMQ

Обработка (consumer):

  CLI Worker → AMQP Transport ← RabbitMQ → MessageBus → Message Handler
```

## 8. Как работает фабрика маршрутов под капотом

`AbstractMessengerFactory` делает две вещи:

**`createBus()`** — собирает Symfony MessageBus:

```
routes() → MessengerBusConfigBuilder::build() → MessengerBusFactory::create() → MessageBus
```

1. `routes()` возвращает список `MessengerRouteDto` (сообщение + handler + очередь).
2. `MessengerBusConfigBuilder` превращает маршруты в конфигурацию: handlers, routing, transports.
   Handler'ы резолвятся **лениво** через ServiceLocator — объекты не создаются, пока сообщение не придёт.
3. `MessengerBusFactory` собирает `MessageBus` с двумя middleware:
   - `SendMessageMiddleware` — отправляет сообщение в AMQP-транспорт;
   - `HandleMessageMiddleware` — вызывает handler при получении из очереди.

**`createPublisher()`** — оборачивает bus в `MessengerMessagePublisher` с дедупликацией:

```
createBus() + DedupCacheInterface → MessengerMessagePublisher
```

## 9. Как работает консьюмер

Консьюмер — это Symfony Messenger `Worker`, обёрнутый в `ConsumerRunner` (`rebit.share`).

Доменные runner'ы (например, `FacetConsumerRunner`) только маппят свой enum на транспорт/очередь
и делегируют всю инфраструктурную работу в `ConsumerRunner`.

**Цепочка вызова:**

```
CLI-команда → UseCase → FacetConsumerRunner → ConsumerRunner (share)
```

**Что делает `ConsumerRunner`:**

1. Создаёт `EventDispatcher` с подписчиками:
   - `StopWorkerOnMessageLimitListener` — остановка по лимиту сообщений;
   - `StopWorkerOnTimeLimitListener` — остановка по лимиту времени;
   - `SendFailedMessageForRetryListener` — повторная обработка при ошибке (если задана retry-стратегия);
   - `SendFailedMessageToFailureTransportListener` — отправка в failed-очередь после исчерпания попыток.
2. Создаёт `Worker` с транспортом нужной очереди и bus.
3. Worker слушает очередь в цикле, достаёт сообщения, вызывает handler через bus.

Защита от параллельного запуска — ответственность CLI-команды (`#[WithLock]`), а не runner'а.

### Retry-стратегия

При падении handler'а сообщение повторно отправляется в ту же очередь с задержкой.
По умолчанию используется `MultiplierRetryStrategy`:

| Попытка | Задержка |
|---------|----------|
| 1       | 1 сек    |
| 2       | 2 сек    |
| 3       | 4 сек    |

После исчерпания попыток сообщение уходит в failed-очередь (`MessengerQueueEnum::FAILED`).
Retry-стратегия и failed-транспорт настраиваются в DI при создании `ConsumerRunner`.

### Запуск

```bash
php bin/cli.php app:facet:update-consume --limit=500 --time-limit=50
php bin/cli.php app:facet:reindex-consume --limit=10 --time-limit=300
```

## 10. Чего делать не надо

- **Отправлять сообщение напрямую через `MessageBusInterface`** — используйте `MessagePublisherInterface` через фабрику. Bus не знает про дедупликацию.
- **Создавать сообщение без наследования от `AbstractMessage`** — publisher принимает только `AbstractMessage`.
- **Класть тяжёлые объекты в сообщение** — сообщение сериализуется в очередь. Кладите только ID и скаляры, а в handler доставайте данные из БД/индекса.
- **Ловить исключения в handler без re-throw** — если handler проглотит ошибку, Messenger не узнает о сбое и не выполнит retry. Сообщение будет считаться успешно обработанным.
- **Делать handler с состоянием** — handler должен быть stateless. Все данные приходят через сообщение.
- **Регистрировать handler напрямую без фабрики маршрутов** — используйте `AbstractMessengerFactory` и `MessengerRouteDto`, чтобы маршруты были в одном месте.

## Что нужно запомнить

1. Сообщение — наследник `AbstractMessage`, лежит в `Application/<Domain>/Message/`.
2. Handler — `__invoke()`, лежит рядом в подпапке `Handler/`.
3. Фабрика маршрутов — наследник `AbstractMessengerFactory`, лежит в `Infrastructure/<Domain>/Messenger/`.
4. Publisher получаем через `YourFactory::createPublisher($locator)` в DI.
5. Отправить сообщение можно — из Application и Infrastructure.
6. Консьюмер — CLI-команда → UseCase → доменный runner → `ConsumerRunner` (share).
7. Retry — 3 попытки с нарастающей задержкой, потом failed-очередь. Настраивается в DI.
8. Дедупликация — параметр `deduplicateTime` в `dispatch()`. Максимум 2 отправки за окно.
9. В сообщение кладём только скаляры и ID, не объекты.
