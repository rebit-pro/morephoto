# PHP: правила и архитектурные ограничения

Эта глава не про архитектуру слоёв, а про связь качества кода с архитектурными решениями.

Подробные правила оформления кода, нейминга, типизации и phpDoc описаны в отдельном каталоге:

> **[Правила написания кода](../code-writing-rules/README.md)** — полный набор конвенций по стилю, форматированию и практикам.

Здесь перечислены только те аспекты стиля, которые напрямую влияют на архитектуру и её устойчивость.

## 1. Почему стиль важен для архитектуры

Хорошая архитектура быстро разваливается, если базовый код:

- нестрого типизирован — ошибки обнаруживаются слишком поздно;
- опирается на неявные приведения — поведение становится непредсказуемым;
- везде выглядит по-разному — ревью превращается в спор о вкусах.

## 2. `final readonly` и архитектура

`final readonly` это не просто стилистическое решение. Оно напрямую связано с DI-моделью проекта.

Все сервисы живут как Singleton в рамках запроса. Если сервис хранит изменяемое состояние, поведение начинает зависеть от порядка вызовов.

`final readonly` защищает от этого:

- `readonly` запрещает изменение состояния после создания;
- `final` запрещает наследование, которое может добавить скрытое состояние.

| Тип класса | Обычно |
|---|---|
| DTO, ValueObject | `final readonly` |
| UseCase | `final readonly` |
| Service без изменяемого состояния | `final readonly` |
| Builder | `final readonly` |
| Adapter | `final readonly` |

## 3. Типизация и порты

Строгая типизация аргументов, возвращаемых значений и свойств критична для портов.

Если порт возвращает `mixed` или `array` без phpDoc shape, то:

- вызывающий код не знает контракт;
- IDE и phpStan не могут проверить правильность;
- ошибки вылезают в runtime, а не при написании.

Для сложных массивов обязателен phpDoc в shape-формате с переносом:

```php
/** @var array<int, array{
 *     id: int,
 *     name: string,
 * }> */
```

## 4. `ServiceLocator` и зависимости

`ServiceLocator` допустим только в DI-конфигах, `include.php`, bootstrap и интеграционных entrypoint.

Если `ServiceLocator` появляется в UseCase, Builder или Domain, это нарушение архитектуры: зависимость перестаёт быть явной и класс невозможно протестировать.

## 5. Производительность на hot path

В каталоге это особенно важно. В чувствительных местах не нужно плодить:

- лишние циклы;
- `array_merge` в цикле;
- spread-оператор;
- промежуточные массивы.

Это не означает нечитаемый код. Это означает осознанный выбор структуры данных.

## 6. Короткий checklist перед завершением задачи

| Проверка | |
|---|---|
| В файле есть `declare(strict_types=1);` | |
| Все аргументы и возвращаемые значения типизированы | |
| Есть `final readonly`, где это уместно | |
| Нет `empty()` и неявных проверок | |
| Нет магических числовых ID (используйте Enum) | |
| Сложные массивы описаны через phpDoc shape | |
| Новый код отформатирован под `php-cs-fixer` проекта | |
| Логика лежит в правильном слое | |
| `ServiceLocator` не используется в бизнес-коде | |

## Что нужно запомнить

1. Подробные правила стиля описаны в [code-writing-rules](../code-writing-rules/README.md).
2. `final readonly` — не косметика, а защита Singleton-модели DI.
3. Строгая типизация — основа надёжных контрактов между слоями.
4. `ServiceLocator` в бизнес-коде — нарушение архитектуры.
