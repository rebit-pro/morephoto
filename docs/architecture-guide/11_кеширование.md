# Кеширование


## 1. Базовое правило проекта

Для нового прикладного кода правило такое:

1. кэшируем через `Cache` facade.
2. `cacheId` и `ttl()` храним в `*CacheEnum`, чтобы легко видеть все места, где используется этот ключ.
3. при пересборке источника данных явно чистим связанный кэш через методы `Cache::forget*`.

Это не означает, что вообще нигде не может быть технической строковой константы кэша.
Во внутренней инфраструктуре `rebit.share` есть служебные кэши вроде `dto_metadata`.
Но для feature-кода и `UseCase` строковые ключи не должны разъезжаться по проекту.

## 2. Как выбирать способ кэширования

| Сценарий | Метод | Как инвалидировать |
|---|---|---|
| Один готовый результат целиком | `Cache::remember(...)` | `Cache::forgetRemember(cacheId)` |
| Кэш-словарь по ключу внутри одной директории | `Cache::rememberArrayValue(...)` | `Cache::forgetArrayValue(cacheId, key)` или `Cache::forgetArrayDir(cacheId)` |
| Данные завязаны на Bitrix tags | `Cache::rememberTagged(...)` | `Cache::forgetTagged(tag)` |
| Накопительный тегированный кэш-массив | `Cache::updateTagged(...)` | обычно `Cache::forgetTagged(tag)` |

## 3. Публичный API `Cache` facade

Полный публичный API у `Rebit\Share\Shared\Facade\Cache` сейчас такой:

| Метод                                                                                                                                               | Назначение | Где использовать |
|-----------------------------------------------------------------------------------------------------------------------------------------------------|---|---|
| `setCache(?ManagedCache $cache): void`                                                                                                              | подмена managed cache | только тесты |
| `setTaggedCache(?TaggedCache $taggedCache): void`                                                                                                   | подмена tagged cache | только тесты |
| `setDataCache(?DataCache $dataCache): void`                                                                                                         | подмена data cache | только тесты |
| `remember(callable $callback, string $cacheId, int $ttl = 3600, bool $clearOnDeploy = false): mixed`                                                | managed cache по одному ключу | основной сценарий для одного результата |
| `rememberArrayValue(callable $callback, string $cacheId, int\|string $key, int $ttl = 3600, bool $clearOnDeploy = false): mixed`                    | data cache по директории и ключу | словари, lookup-map, metadata cache |
| `rememberTagged(callable $callback, string $cacheId, string $cacheDir = '', array $tags = [], int $ttl = 3600, bool $clearOnDeploy = false): mixed` | data cache + tagged cache | когда нужна инвалидация по тегам |
| `updateTagged(string $cacheId, string $cacheDir, array $newData, array $tags = [], int $ttl = 3600): array`                                         | обновление накопительного тегированного кэша | только для merge-сценариев |
| `forgetRemember(string $cacheId): void`                                                                                                             | удаляет запись из `remember(...)` | managed cache invalidation |
| `forgetArrayValue(string $cacheId, int\|string $key): void`                                                                                         | удаляет одно значение из `rememberArrayValue(...)` | точечная очистка словаря |
| `forgetArrayDir(string $cacheId): void`                                                                                                             | удаляет всю директорию array/data cache | полная очистка словаря |
| `forgetTagged(string $tag): void`                                                                                                                   | инвалидирует записи по одному tag | стандартная tag invalidation |

### Что важно помнить про API

- `remember(...)` использует `ManagedCache`;
- `rememberArrayValue(...)` и `rememberTagged(...)` используют `DataCache`;
- у `rememberArrayValue(...)` параметр `cacheId` по факту играет роль директории кэша;
- `rememberArrayValue(...)` вызывает callback как `$callback($key)`;
- `updateTagged(...)` делает `array_merge($existingData, $newData)`, то есть новые значения перезаписывают старые по одинаковым ключам;
- `forgetTagged(...)` принимает один `string $tag`, а не массив тегов.

## 4. Метод за методом

### `Cache::remember(...)`

Используйте, когда нужно закэшировать один результат целиком.

```php
return Cache::remember(
    static fn(): array => $this->promotionListAdapter->getProductActivePromotionsInCurrentRegion(),
    cacheId: ProductCacheEnum::PRODUCTS_PROMOTION_LIST->value,
    ttl: ProductCacheEnum::PRODUCTS_PROMOTION_LIST->ttl(),
);
```

Подходит для:

- списка акций;
- breadcrumbs;
- SEO-данных;
- результата одного запроса по одному набору параметров.

Чистится через:

```php
Cache::forgetRemember(ProductCacheEnum::PRODUCTS_PROMOTION_LIST->value);
```

### `Cache::rememberArrayValue(...)`

Используйте, когда у вас один cache-dir и много отдельных значений по ключу.

```php
$sections[$sectionId] = Cache::rememberArrayValue(
    fn() => $this->smartFilterDictionaryQuery->getDictionaryBySection($sectionId),
    cacheId: SmartFilterCacheEnum::VALUE_DICTIONARY_ARRAY->value,
    key: $sectionId,
    ttl: SmartFilterCacheEnum::VALUE_DICTIONARY_ARRAY->ttl(),
);
```

Подходит для:

- словаря по `sectionId`;
- справочника по `code`;
- служебных metadata-кэшей.

Если нужно удалить одно значение:

```php
Cache::forgetArrayValue(
    SmartFilterCacheEnum::VALUE_DICTIONARY_ARRAY->value,
    $sectionId,
);
```

Если нужно удалить весь словарь:

```php
Cache::forgetArrayDir(SmartFilterCacheEnum::VALUE_DICTIONARY_ARRAY->value);
```

### `Cache::rememberTagged(...)`

Используйте, когда нужно завязаться на Bitrix tags и инвалидировать данные не по одному cache-id, а по группе сущностей.
Норма здесь та же, что и в остальных сценариях:

- базовый `cacheId` берём из `*CacheEnum`;
- runtime-суффикс добавляем рядом с вызовом;
- `iblock_id_*` tag получаем через `IblockIdEnum`, а не строкой вручную.

```php
return Cache::rememberTagged(
    static fn(): array => $this->bannerRepository->getSectionBanners($sectionId),
    cacheId: BannerCacheEnum::SECTION_BANNER_LIST->value . '_' . $sectionId,
    cacheDir: '/rebit/catalog/banner',
    tags: [IblockIdEnum::BANNERS->toTaggedName()],
    ttl: BannerCacheEnum::SECTION_BANNER_LIST->ttl(),
);
```

Чистится через:

```php
Cache::forgetTagged(IblockIdEnum::BANNERS->toTaggedName());
```

Если нужно очистить несколько тегов, вызывайте `forgetTagged(...)` по одному тегу.

### `Cache::updateTagged(...)`

Это специальный метод для накопительного кэша.
Его не нужно использовать как универсальную замену `rememberTagged(...)`.

Он нужен, когда:

- есть уже накопленный массив;
- надо дозаписать новые элементы;
- нужна та же tag-based invalidation.

Если сценарий не накопительный, `remember(...)` или `rememberTagged(...)` обычно проще и безопаснее.

## 5. `*CacheEnum`

### Где лежит

Кэш enum должен жить в модуле рядом со сценарием:

```text
Application/<Domain>/Enum/*CacheEnum.php
```

### Шаблон

```php
enum FooCacheEnum: string
{
    case LIST = 'foo_list';
    case ITEM = 'foo_item';

    public function ttl(): int
    {
        return match ($this) {
            self::LIST => 3600,
            self::ITEM => 86400,
        };
    }
}
```

### Что в нём хранить

- стабильный `cacheId` в `->value`;
- единый `ttl()` для этого ключа.

### Что не хранить

- случайные суффиксы конкретного вызова;
- runtime-параметры вроде `sectionId`, `cityId`, `userId`.

То есть правильно так:

```php
cacheId: SeoCacheEnum::META_TAGS_CACHE->value . '_' . $sectionId
```

а не так:

```php
cacheId: 'meta_tags_cache_' . $sectionId
```

### Актуальные `*CacheEnum` в проекте

| Enum | Кейсы | TTL |
|---|---|---|
| `BannerCacheEnum` | `SECTION_BANNER_LIST` | `3600` |
| `CatalogCacheEnum` | `PROPERTY_DICTIONARY` | `86400` |
| `ProductCacheEnum` | `PRODUCTS_PROMOTION_LIST` | `3600` |
| `SeoCacheEnum` | `META_TAGS_CACHE`, `BREADCRUMBS_CACHE` | `86400` |
| `SmartFilterCacheEnum` | `ADMIN_SECTION_CONFIG`, `VALUE_DICTIONARY_ARRAY`, `STORES_IN_CITY_ARRAY` | `3600`, `3600`, `86400` |

## 6. Инвалидация через `Cache` facade

Инвалидация тоже описывается через `Cache`, а не через отдельный generic-контракт.

| Метод | Когда использовать |
|---|---|
| `forgetRemember(string $cacheId): void` | для кэша из `remember(...)` |
| `forgetArrayValue(string $cacheId, int|string $key): void` | для точечной очистки `rememberArrayValue(...)` |
| `forgetArrayDir(string $cacheId): void` | для полной очистки `rememberArrayValue(...)` |
| `forgetTagged(string $tag): void` | для `rememberTagged(...)` и `updateTagged(...)` |

### Реальный эталон инвалидации

Для `SmartFilter` инвалидация по смыслу должна выглядеть так:

```php
Cache::forgetRemember(SmartFilterCacheEnum::ADMIN_SECTION_CONFIG->value);
Cache::forgetArrayDir(SmartFilterCacheEnum::STORES_IN_CITY_ARRAY->value);
// ...
Cache::forgetArrayDir(SmartFilterCacheEnum::VALUE_DICTIONARY_ARRAY->value);
```

Правило здесь простое:

- пересобрали источник данных -> почистили связанные cache keys/dirs/tags;
- не чистим кэш «на глаз» без привязки к конкретному enum и конкретному типу кэша.

## 7. `clearOnDeploy`

У методов `remember(...)`, `rememberArrayValue(...)` и `rememberTagged(...)` есть параметр `clearOnDeploy`.

Что он делает:

- берёт timestamp из `.git/refs/heads/master`;
- добавляет его к `cacheId`;
- после деплоя ключ автоматически меняется.

Используйте `clearOnDeploy`, когда кэш зависит от структуры кода или метаданных, а не только от предметных данных.

Хороший пример:

- metadata DTO;
- reflection cache;
- технические кэши инфраструктуры.

Плохой пример:

- обычный бизнес-кэш, который должен инвалидироваться предметным событием.

## 8. Кэширование объектов и `__clone()`

`Cache` facade делает глубокое клонирование данных при чтении и записи.
Это защищает от побочного эффекта Bitrix-кэша, когда объект после чтения случайно мутируют и он фактически меняется и в кэше.

Правила такие:

- `final readonly` объект можно кэшировать спокойно;
- mutable-объект лучше не кэшировать;
- если кэшируете mutable-объект, реализуйте `__clone()`;
- если реализовали `__clone()`, сами отвечаете за клонирование вложенных объектов.

Если `__clone()` нет, фасад клонирует через Reflection.
Это корректно, но заметно медленнее.
Для таких случаев `Cache` один раз пишет warning в `LogChannelEnum::todo`.

## 9. Антипаттерны

- строковые `cacheId` прямо в `UseCase`, когда это обычный прикладной кэш;
- разный `ttl()` для одного и того же cache key в разных местах;
- использование `rememberArrayValue(...)`, если нужен обычный один результат;
- использование `remember(...)`, если на самом деле нужен кэш-словарь по ключу;
- очистка `forgetArrayDir(...)` там, где должен быть `forgetRemember(...)`;
- попытка очистить несколько тегов через несуществующий `forgetTagged(array $tags)`;
- кэширование mutable DTO без `__clone()`;
- молчаливое использование дефолтного `3600` вместо явного `ttl()` из enum.

## Что нужно запомнить

1. Для нового feature-кода кэш оформляется через `Cache` facade и `*CacheEnum`.
2. `remember`, `rememberArrayValue` и `rememberTagged` это три разных сценария, а не взаимозаменяемые методы.
3. Инвалидация должна идти через `Cache::forget*` и соответствовать типу кэша.
4. `clearOnDeploy` нужен для технических кэшей, а не как замена нормальной предметной инвалидации.
5. `final readonly` объекты кэшируются безопаснее и быстрее, чем mutable-структуры.
