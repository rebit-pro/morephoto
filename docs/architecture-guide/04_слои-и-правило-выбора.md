# Слои и правило выбора

Эта глава отвечает на главный практический вопрос: «Куда положить код?»

Если разработчик ошибается со слоем, проблемы появляются сразу:

- бизнес-логика оказывается в шаблоне;
- SQL уезжает в `UseCase`;
- legacy API начинает торчать в `Presentation`;
- повторное использование становится дорогим.

# Домен (бизнесовая единица) и слои
В домене выделяется:
- **бизнес-логика**, которая ложится в папку `Domain/<имя домена>`
- **логика оркестрации** (объединение бизнес правил с инфраструктурой и отдача потребителям), которая ложится в папку `Application/<имя домена>`

В других слоях нет внутри деления на домены, но может быть также папка с именем домена, если она группирует в себе компоненты, шаблоны или инфраструктуру, которая относится к этому домену. 

## Краткая таблица слоёв

| Слой | Что означает | Что там живёт | Чего там быть не должно |
|---|---|---|---|
| `Domain` | предметное ядро | сущности, value object (объекты-значения), доменные сервисы, репозитории ORM/SQL проекта | HTTP, шаблоны, Bitrix-компоненты, orchestration (оркестрация) сценария |
| `Application` | сценарий использования | `UseCase`, прикладной сервис (application service), порты, DTO сценария | прямой Elastic, `ServiceLocator`, шаблонная логика |
| `Infrastructure` | внешние детали | Elastic, HTTP, адаптер legacy, Bitrix-специфичный код (кроме ORM), интеграции | предметные правила, логика отображения |
| `Presentation` | вход и выход системы | component builder, view model, controller, command | доступ к raw SQL/Elastic, тяжёлая бизнес-логика |
| `Shared` | переиспользуемые общие вещи | enum, helper (хэлпер), value object (объект-значение), исключения, утилиты | логика, которая привязана к одному предметному сценарию |

## Как понять, что такое «предметная логика»

Предметная логика отвечает на вопрос бизнеса.
Например:

- какие баннеры показывать на странице;
- как вычислить набор доступных фильтров;
- как проверить валидность состояния сущности;
- как отобрать акции для товара.

Техническая логика отвечает на вопрос инфраструктуры.
Например:

- как сделать запрос в Elastic;
- как распарсить HTTP-запрос (request);
- как зарегистрировать маршрут (route);
- как обратиться к Bitrix API.

## Правило выбора слоя

Используйте этот порядок проверки.

### Шаг 1. Код знает про внешний мир?

Если код зависит от:

- Bitrix API;
- HTTP;
- Elastic;
- файловой системы;
- очередей;
- legacy-классов;

то почти всегда это `Infrastructure`.

### Шаг 2. Код только подготавливает отображение?

Если код:

- собирает данные для шаблона;
- формирует JSON-ответ;
- оркестрирует данные для CLI-вывода;
- собирает view model (модель представления);

то это `Presentation`.

### Шаг 3. Код выражает предметное правило?

Если код:

- описывает состояние сущности;
- содержит инвариант;
- реализует доменное правило;
- работает с предметной коллекцией или репозиторием;

то это `Domain`.

### Шаг 4. Код склеивает шаги сценария?

Если код:

- вызывает несколько зависимостей;
- координирует сценарий;
- работает через порты;
- собирает результат сценария;

то это `Application`.

## Схема принятия решения

```text
Это про внешний мир?
    yes -> Infrastructure
    no
        |
        v
Это только про отображение / API / CLI?
    yes -> Presentation
    no
        |
        v
Это про предметное состояние или правило?
    yes -> Domain
    no
        |
        v
Это orchestration (оркестрация) сценария?
    yes -> Application
    no
        |
        v
Скорее всего Shared или неверно сформулирована задача
```

## Протекание между слоями

Протекание между слоями это ситуация, когда код одного слоя начинает знать типы, правила или технические детали другого слоя.

Примеры:

- `Domain` принимает `HttpRequest`;
- `Application` возвращает готовый `JsonResponse` или HTML-строку;
- `Presentation` работает с raw-ответом Elastic вместо нормального DTO;
- межмодульный контракт начинает тащить внутренний DTO конкретного модуля.

Почему это плохо:

- слой теряет свою ответственность;
- изменения в одном месте начинают ломать чужой слой;
- код становится трудно переиспользовать;
- тестирование требует поднимать лишнюю инфраструктуру.

### Как заметить протекание

Обычно оно видно по нескольким сигналам.

- В сигнатуре метода появились типы чужого слоя: `Request`, `JsonResponse`, `Client`, Bitrix legacy-класс.
- `UseCase` начинает возвращать данные в формате шаблона или API-ответа.
- `Domain` или `Application` знают названия HTTP-полей, ключи JSON или структуру шаблона.
- `Presentation` тянет SQL, Elastic или Bitrix API напрямую, вместо вызова сценария.
- Для теста доменного правила приходится поднимать HTTP, Bitrix bootstrap или внешний клиент.

Хороший практический вопрос на ревью:

«Если завтра поменяется способ доставки данных наружу, придётся ли менять `Domain` или `Application`?»

Если ответ «да», значит граница слоёв уже протекает.

### Как избежать протекания

Используйте простое правило:

- `Presentation` преобразует request (запрос) в `RequestDto` или `InputDto`;
- `Application` оркестрирует сценарий и возвращает `OutputDto`;
- `Infrastructure` прячет Bitrix, HTTP, Elastic, legacy и маппит их во внутренние DTO;
- `Domain` работает только с предметными сущностями, value object (объектами-значениями), коллекциями и репозиториями.

Практически это означает:

- не передавать `Request`, `Response`, raw-массивы внешнего API и Bitrix-объекты глубже нужного слоя;
- не возвращать из `UseCase` view model (модель представления), HTML или структуру шаблона;
- описывать потребность через порт в слое-потребителе, а реализацию держать в `Infrastructure`;
- выносить межмодульные DTO в `rebit.share`, если они становятся контрактом между модулями.

Если сомневаетесь, разделяйте две вещи:

- зависимости в коде;
- движение данных.

### Кто о ком может знать в коде

Зависимость в коде это когда класс:

- импортирует тип;
- принимает зависимость в конструктор;
- вызывает методы другого класса напрямую.

Допустимые направления:

- `Presentation -> Application`: **Presentation** вызывает только `UseCase` из **Application**, при том из любых доменов  
- `Application -> Domain`: **Application** использует любые классы из **Domain**, но только внутри своего домена. Если нужны данные из другого домена см. [Кросс-доменное взаимодействие](06_кросс-доменное-взаимодействие.md)
- `Infrastructure -> Application`: **Infrastructure** реализует интерфейсы, объявленные в **Application**
- `Infrastructure -> Domain`: **Infrastructure** реализует интерфейсы, объявленные в **Domain** (у нас это редко, т.к. Bitrix-ORM можно прямо в репозитории домена)

Примеры:

- `Presentation -> Application` — `CatalogSectionBuilder` вызывает `FacetProductListQueryUseCase`, чтобы получить данные для компонента.
- `Application -> Domain` — `UseCase` вызывает `FacetRepository` или доменный сервис, чтобы получить предметные данные и применить правило.
- `Infrastructure -> Application` — `ElasticFacetProductListQuery` реализует `FacetProductListQueryInterface`, то есть инфраструктура зависит от application-контракта.
- `Infrastructure -> Domain` — адаптер или интеграция маппит внешний ответ в доменный `ValueObject`, сущность или коллекцию. У нас это крайне редкий случай 

Недопустимые направления:

- `Domain -> Application`: домен изолированная единица, которая не знает ни о ком, кроме Shared, даже о других доменах.
- `Domain -> Presentation`: вся бизнес-логика попадает в **Presentation** через UseCase в **Application**.
- `Domain -> Infrastructure`: если у домена есть интерфейсы, то их реализуем в инфраструктуре, но домен об это ничего не знает.
- `Application -> Presentation`: **Application** не знает, как и где используются его UseCase.  
- `Application -> Infrastructure`: **Application** имеет интерфейсы-контракты для получения данных из **Infrastructure**, но не знает кто и как их реализовал.
- `Infrastructure -> Presentation`: **Presentation** использует UseCase с готовыми для него данными или отдаёт их в UseCase. Как они используются дальше — ему не важно.

Примеры:

- `Domain -> Application` — сущность товара не должна вызывать `ReindexProductUseCase` или любой другой `UseCase`.
- `Domain -> Presentation` — доменный сервис не должен знать, что в JSON есть поле `seoTitle` или что шаблону нужен массив `items`.
- `Domain -> Infrastructure` — доменная логика не должна вызывать `ServiceLocator` или `Elastic\Client`.
- `Application -> Presentation` — `UseCase` не должен возвращать `CatalogSectionViewModel`, HTML или массив для шаблона.
- `Application -> Infrastructure` — `UseCase` не должен принимать в конструктор `Elastic\Client`, HTTP-клиент или Bitrix legacy-класс.
- `Infrastructure -> Presentation` — адаптер не должен зависеть от builder, controller, view model (модели представления) или собирать данные в формат шаблона.

`Shared` можно использовать из любого слоя, если он не тащит в себя сценарную или Bitrix-специфичную логику.

### Как могут двигаться данные

Запрос или команда обычно идут так:

`внешний мир потребитель данных -> Presentation -> Application -> Port -> Infrastructure -> внешний мир поставщик данных`

Примеры:

- `внешний мир -> Infrastructure -> Application -> Presentation` — Elastic (внешний мир) вернул raw-ответ, инфраструктурный адаптер преобразовал его в `OutputDto`, `UseCase` отдал результат builder или controller.
- `Domain -> Application -> Presentation` — репозиторий вернул сущности или коллекцию, `UseCase` собрал `OutputDto`, `Presentation` превратил его в view model (модель представления) или JSON.

Главное правило:

- `Application` может использовать данные, которые вернул `Domain`;
- `Domain` не должен знать, что его вызывает `Application`;

- внешний мир должен заканчиваться в `Infrastructure`;
- формат отображения должен начинаться и заканчиваться в `Presentation`;
- между ними лучше передавать свои DTO и предметные типы, а не технические объекты.

## Примеры из проекта

| Пример | Правильный слой | Почему |
|---|---|---|
| `CatalogSectionBuilder` | `Presentation` | собирает страницу каталога для компонента |
| `FacetProductListQueryUseCase` | `Application` | orchestration (оркестрация) сценария получения товаров |
| `PromotionListAdapter` | `Infrastructure` | прячет legacy-источник акций |
| `FacetRepository` | `Domain` | держит SQL и предметные запросы в домене |

## Что чаще всего путают

### Ошибка 1. SQL в `UseCase`

Неправильно:

```php
final readonly class GetProductsUseCase
{
    public function execute(): array
    {
        return Application::getConnection()->query('SELECT ...')->fetchAll();
    }
}
```

Почему плохо:

- сценарий начинает знать детали БД;
- такой код трудно переиспользовать;
- нарушается ответственность слоя.

Правильно:

- SQL или ORM-запрос уходит в репозиторий `Domain`;
- `UseCase` вызывает репозиторий или порт.

### Ошибка 2. Бизнес-логика в builder

Неправильно:

- builder сам вычисляет предметное правило;
- builder решает, какой баннер «по бизнесу» валиден;
- builder делает выборку из Bitrix напрямую.

Правильно:

- builder собирает сценарии (use case) из любых доменов;
- use case и доменные сервисы решают предметную задачу;
- builder только готовит представление.

### Ошибка 3. Форматирование в `UseCase`

`UseCase` не должен решать, как выводить строку в шаблоне или как называть поле ответа.
Это уже `Presentation`.

## Кросс-доменные зависимости внутри модуля

Это тонкая тема, потому что в живом проекте есть и целевой стандарт, и существующие переходные решения.

### Целевой стандарт

Если домену нужна функциональность другого домена, зависимость должна быть осознанной:

- либо через application-контракт;
- либо через порт и адаптер;
- либо через общий межмодульный контракт в `rebit.share`, если речь о связи модулей.

Подробно с примерами: [06. Кросс-доменное взаимодействие](./06_кросс-доменное-взаимодействие.md).

## `Shared` и `Contracts`

### `Shared` внутри модуля

Используйте `lib/Shared`, если сущность нужна только этому модулю:

- enum;
- value object (объект-значение);
- исключение (exception);
- helper (хэлпер);
- маленькая утилита.

### `Contracts` в `rebit.share`

Используйте `rebit.share/lib/Contracts/<Domain>`, если контракт нужен двум и более модулям.

## Что нужно запомнить

1. Слой выбирается по ответственности, а не по вкусу.
2. Если код знает про Bitrix/Elastic/legacy, это сильный сигнал к `Infrastructure`.
3. Если код собирает сценарий, это `Application`.
4. Если код готовит шаблон или JSON, это `Presentation`.
5. Если код выражает правило предметной области, это `Domain`.
