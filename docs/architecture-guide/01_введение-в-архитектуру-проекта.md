# Введение в архитектуру проекта

## Зачем вообще нужна эта документация

Проект большой, живёт давно и сочетает в себе:

- legacy (исторический) код;
- Bitrix-специфику;
- новую архитектуру;
- постепенную миграцию между ними.

Если у команды нет единого языка и единых правил, то очень быстро появляются проблемы:

- бизнес-логика размазывается по шаблонам, компонентам и контроллерам;
- legacy-подходы начинают копироваться в новый код;
- ревью превращается в спор о вкусах, а не о качестве решения;
- перенос старого кода в новую архитектуру идёт хаотично.

Эта документация нужна, чтобы у команды был один учебный маршрут:

1. понять, какие архитектуры применяются;
2. понять, зачем каждая из них нужна;
3. увидеть, как они выражаются в коде проекта;
4. получить конкретные правила для нового кода.

## Что считать нормой

Нормой для нового кода считаем:

- правила, описанные в этой документации;
- реальные проектные соглашения, которые уже поддерживаются в коде и в ревью;
- эталоны из модулей, которые ближе всего к новой архитектуре.

## Какие архитектуры используются в проекте

В проекте не одна архитектура, а несколько идей, которые работают вместе.

| Подход | Что это значит простыми словами | Зачем он нужен в проекте |
|---|---|---|
| DDD | код раскладывается по предметным областям и слоям | чтобы бизнес-логика жила не в Bitrix-скриптах, а в понятных доменах |
| Hexagonal / Ports & Adapters | приложение зависит от контрактов, а не от конкретного Elastic, HTTP или legacy API | чтобы менять источник данных без переписывания сценариев |
| MVVM для компонентов | шаблон получает удобную модель представления, а не сырые данные и бизнес-логику | чтобы шаблоны были простыми и предсказуемыми |

## 1. DDD (Domain-Driven Design) в этом проекте

### Что означает DDD здесь

На практике это означает три вещи:

1. Код группируется по предметным зонам, то есть доменам: `Wallet`, `Identity`, `Auth`, `Bybit` и т.д.
2. Внутри модуля есть разделение на слои: `Domain`, `Application`, `Infrastructure`, `Presentation`, `Shared`.
3. Предметная логика не должна жить в случайных технических точках вроде `class.php`, контроллерах или шаблонах.

### Почему это важно

Когда предметная логика лежит рядом с Bitrix API, её трудно:

- переиспользовать;
- тестировать;
- переносить;
- безопасно менять.

DDD позволяет сказать: «Вот это правило каталога», а не «Вот это случайный кусок кода внутри шаблона».

## 2. Hexagonal Architecture в этом проекте

### Что это значит

Hexagonal architecture здесь означает простую идею:

- `Application` знает, что ему нужно;
- но не знает, как это конкретно реализовано снаружи.

Эта потребность описывается портом.
А конкретная реализация живёт в адаптере инфраструктуры.

### Схема

```text
Presentation
    |
    v
Application / UseCase
    |
    v
Port (интерфейс)
    |
    v
Infrastructure Adapter
    |
    v
Elastic / Bitrix / HTTP / legacy
```

### Почему это важно

Если сценарий напрямую знает про конкретный `HttpClient`, то его нельзя нормально переиспользовать и трудно заменить.
Если он знает только интерфейс (порт), реализацию можно сменить без изменения сценария.

## 3. MVVM (Model-View-ViewModel) в Bitrix-компонентах

> ⚠️ В текущей версии Rebit P2P фронтенд реализован на Vue 3 SPA. Этот паттерн описан для справки.

### Что это значит

Для компонентов мы используем поток:

```text
ParamsDto -> Builder -> ResultDto -> ViewModel -> template
```

### Что означает каждая часть

| Часть | Что делает |
|---|---|
| `ParamsDto` | описывает вход компонента строгими типами |
| `Builder` | собирает данные через use case (сценарии) |
| `ResultDto` | хранит результат сборки |
| `ViewModel` | даёт шаблону удобный интерфейс (API представления) |
| `template` | только отображает |

### Почему это важно

Если шаблон получает «сырой мир» из Bitrix и сам начинает решать бизнес-задачи, проект быстро теряет управляемость.
MVVM нужен, чтобы шаблон не занимался оркестрацией.

## Как эти подходы работают вместе

Ниже типовой поток для Bitrix-компонента:

```text
Страница
  -> создаёт ComponentParamsDto
  -> вызывает IncludeComponent
  -> component class.php
  -> Builder
  -> UseCase
  -> Port
  -> Infrastructure Adapter
  -> внешняя система / legacy-источник / Elastic
  -> ResultDto
  -> ViewModel
  -> template
```

Типовой поток для API:

```text
HTTP request
  -> routes.php
  -> Controller action
  -> RequestDto
  -> UseCase
  -> Port / Domain / Repository
  -> Response DTO
  -> json()/created()/noContent()
```

## Что является эталонами в проекте

| Задача | Где смотреть |
|---|---|
 UseCase, DI и структура модуля  `api/public/local/modules/rebit.wallet` 
 базовые инфраструктурные классы, общие контракты  `api/public/local/modules/rebit.share` 
 JSON API и контроллеры  `api/public/local/modules/rebit.identity` 


## Как относиться к legacy

Legacy в проекте существует как факт.
Запрещено не его наличие, а перенос legacy-подхода в новый код без необходимости и без явной маркировки.

Правильное отношение:

1. Изолировать legacy в `Infrastructure/LegacyAdapter`, если его нельзя перевести сейчас на новые рельсы.
2. Поверх него строить новый `UseCase`.
3. Позже заменить адаптер, не ломая `Presentation` и `Application`.

## Главные правила, которые нужно запомнить с этой главы

1. Мы не пишем «чистый DDD ради DDD», мы пишем управляемый код для долгоживущего проекта.
2. Новая логика должна укладываться в слои, а не в случайные технические точки.
3. `Application` должен зависеть от контрактов (интерфейсов) и доменных правил (сервисы), а не от деталей Bitrix, Elastic и legacy.
4. Шаблон и контроллер должны быть тонкими.
5. Любое отклонение от стандарта нужно явно обосновать.
