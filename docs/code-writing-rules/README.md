## Зачем они?

Облегчить работу разработчикам: меньше писать, меньше думать и при этом больше реализовывать.

- Уменьшить временные затраты на чтение чужого кода и написание своего кода: улучшение автодополнения в IDE, понимания сути объектов, их методов и зависимостей без погружения в реализацию, единый стиль кода - легче восприятие.
- Позволить думать о реализации бизнес логики, а не о технической части: обработке ошибок, логирование, кеширование, формирование ответа сервисам и пр.
- Сделать итоговый код максимально простым.
- Сделать код тестируемым, чтобы после введения тестирования тесты можно было писать легко и быстро.
- Уменьшить связность и упростить рефакторинг.
- Сделать систему более стабильной и отказоустойчивой за счет строгой типизации и быстрых выходов при ошибках.
- Подтянуть проект к современному уровню.

## Какой должен быть код?

1. **Предсказуемым** — без магии и неявного поведения, кроме исключительных случаев.
2. **Строго типизированным**
   - Указывать типы входящих параметров функции.
   - Указывать тип возвращаемых значений функции. Прописывать `void` в качестве возвращаемого значения для void-функций.
   - Использовать режим строгой типизации при создании новых PHP-файлов: https://www.php.net/manual/ru/language.types.declarations.php (см. раздел "Строгая типизация"). Изменить в PhpStorm шаблон для создания новых классов Settings → Editor → File and Code Templates → справа меняем шаблоны PHP Class, PHP Interface, PHP Trait, PHP Enum.

3. **Читаемым** — для команды, а не только автора
4. **Структурированным** — соглашения и стандарты, применение SOLID, DRY, KISS, YAGNI, применение паттернов проектирования.
5. **Минимум статики** — используем DI
6. **Тестируемым**

## Как добиться читаемости?

1. Соблюдение базовых принципов оформления кода по стандартам [PSR1](https://www.php-fig.org/psr/psr-1/) и [PSR12](https://www.php-fig.org/psr/psr-12/)
2. Согласованный и единообразный нейминг классов, методов, переменных, констант и пр.
3. Соблюдение соглашений по единообразию оформлению сравнений, приведений типов, конкатенации и пр. технических моментов.
4. Обязательно комментирование основных моментов, которые неявно вытекают из названий классов и методов. Если имеется какая-то неочевидная особенность в коде, типа костыля, либо особенность реализации или применения метода, то обязательно нужно об этом написать.
5. Обязательный phpDoc с описанием полей всех iterable (в том числе массивы, коллекции, генераторы, массивов Result-объектов БД), Result-объектов БД, дженериков, которые мы возвращаем из методов или которые являются параметрами методов.
6. Обязательный phpDoc для всех исключений, что может вернуть метод или функция, кроме контроллеров.

**Инструмент php-cs-fixer** — утилита, которая форматирует код в `api/public/local` в нужном формате. При редактировании старого легаси сперва отформатируйте и сделайте коммит, затем делайте работу по задаче.
