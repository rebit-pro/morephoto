# Дополнительные правила разработки

## 1. Следуем принципу DRY
Если вы копируете код — это первый сигнал, что необходимо сделать рефакторинг. Дублирование кода увеличивает риск ошибок и усложняет поддержку.

## 2. Избегаем пересечения сред
Основной репозиторий должен содержать только бизнес-логику. Проверки на тестовую среду, среду разработки или специфические адреса должны быть исключены из модулей и функций (за исключением случаев, когда они специально предназначены для этого).
**Рекомендации:**

- Используйте интерфейсы и моки в тестировании.
- Используйте переменные окружения в средах разработки.
- Используйте DI для передачи переменных в сервисы

```php
// ❌ Плохо (жёсткие проверки в коде)
if ('test' === $_SERVER['APP_ENV']) {
    $dbHost = getenv('DB_HOST');
} else {
    $dbHost = 'localhost';
}
$parser = new ParserConnection($dbHost);

// ✅ Хорошо (используем DI и env-переменные)
final readonly class ParserConnection
{
    public function __construct(
        private string $host, // Передаётся из DI
    ) {}
}

// файл .settings.php среды или DI модуля
return [
    'services' => [
        'value' => [
            ParserConnection::class => [
                'className' => ParserConnection::class,
                'constructorParams' => [
                    getenv('DB_HOST'),  // получаем из env
                ],
            ],
        ],
    ],
];
```

## 3. Минимизируем проходы по данным
Избегайте множественного `foreach`, а так же специальных функций для работы с массивами, т.к. они часто создают новые массивы и проходят по ним. Если вы дважды проходите по одному и тому же массиву, подумайте, как обойти его один раз. Это улучшает производительность и читаемость.

### Функции, которых стоит избегать в горячих местах и почему

#### ❌ `array_unique()` — O(n log n) алгоритм, медленнее map-подхода
Функция `array_unique()` внутри использует сортировку для удаления дубликатов, что приводит к `O(n log n)` сложности и создаёт новый массив.

```php
// ❌ Неправильно (медленнее, создаёт новый массив)
$ids = [1, 2, 3, 2, 4, 1, 5];
$unique = array_unique($ids);  // O(n log n)
```

Решение — преобразовать в map через `array_flip()` и вернуть ключи:
```php
// ✅ Правильно (1 проход)
$ids = [1, 2, 3, 2, 4, 1, 5];
$unique = array_keys(array_flip($ids));  // O(n), вернёт [1, 2, 3, 4, 5]

// Или ещё проще через array_fill_keys
$unique = array_keys(array_fill_keys($ids, true));  // O(n)
```

#### ❌ `in_array()` — O(n) на каждый вызов
Если вызываете `in_array()` в цикле, получаете O(n²). Нужно один раз создать map.

```php
// ❌ Неправильно (O(n²))
$allowedIds = [1, 5, 10, 15, 20];
foreach ($products as $product) {
    if (in_array($product->id, $allowedIds, true)) {  // Поиск в массиве ~n операций
        // ...
    }
}

// ✅ Правильно (O(n))
$allowedIds = array_flip([1, 5, 10, 15, 20]);  // Преобразуем в map: [1=>0, 5=>1, 10=>2, ...]
foreach ($products as $product) {
    if (isset($allowedIds[$product->id])) {  // O(1) поиск
        // ...
    }
}
```

#### ❌ `array_merge()` в цикле — создаёт новый массив на каждой итерации
Каждый вызов `array_merge()` копирует всё содержимое предыдущего массива.

```php
// ❌ Неправильно (O(n²))
$result = [];
foreach ($batches as $batch) {
    $result = array_merge($result, $batch);  // На каждой итерации копирует весь $result
}

// ✅ Правильно (O(n))
$result = [];
foreach ($batches as $batch) {
    foreach ($batch as $item) {
        $result[] = $item;  // Добавляем элемент напрямую
    }
}

// Или используем spread operator (если структура однородна)
$result = [...$batches[0], ...$batches[1], ...$batches[2]];  // Для известного количества
```

#### ❌ `array_filter()` + `array_map()` — 2 прохода
Каждая функция делает отдельный проход по массиву.

```php
// ❌ Неправильно (2 прохода)
$prices = [100, 0, 250, 0, 500];
$nonZero = array_filter($prices);  // Проход 1
$doubled = array_map(fn($p) => $p * 2, $nonZero);  // Проход 2

// ✅ Правильно (1 проход)
$doubled = [];
foreach ($prices as $price) {
    if ($price > 0) {  // Фильтр внутри
        $doubled[] = $price * 2;  // Трансформация сразу
    }
}
```

### Паттерн: Map для проверки принадлежности вместо `in_array()` и `array_unique()`

Создаём ассоциативный массив (map), где ключи — это значения, которые нужно проверять. Проверка через `isset()` работает за O(1).

```php
// Пример: есть список ID товаров, нужно фильтровать товары по списку

// Исходные данные
$products = [
    ['id' => 1, 'name' => 'Product A'],
    ['id' => 5, 'name' => 'Product B'],
    ['id' => 10, 'name' => 'Product C'],
    ['id' => 3, 'name' => 'Product D'],
];

// Нужно оставить только товары с ID в списке [1, 10]
$allowedIds = [1, 10];

// Вариант 1: array_flip (ключи и значения меняются местами)
$allowedIdMap = array_flip($allowedIds);  // [1 => 0, 10 => 1]
$filtered = [];
foreach ($products as $product) {
    if (isset($allowedIdMap[$product['id']])) {
        $filtered[] = $product;
    }
}

// Вариант 2: array_fill_keys (явно создаём map с true)
$allowedIdMap = array_fill_keys($allowedIds, true);  // [1 => true, 10 => true]
$filtered = [];
foreach ($products as $product) {
    if (isset($allowedIdMap[$product['id']])) {
        $filtered[] = $product;
    }
}

// Результат: массив с товарами, id которых входят в $allowedIds
```

**Почему это работает быстрее:**
- `in_array()` ищет значение, проходя по всему массиву → O(n)
- `isset()` на map ищет по хешу ключа → O(1)
- При 1000 товаров разница может быть в 100+ раз

**Удаление дубликатов через map:**
```php
// Исходный массив с дубликатами
$ids = [1, 2, 3, 2, 4, 1, 5];

// ❌ Медленнее (O(n log n), создаёт новый массив)
$unique = array_unique($ids);

// ✅ Быстро (через map)
$uniqueMap = [];
foreach ($ids as $id) {
    $uniqueMap[$id] = true;  // Ключ — это значение, дубликаты перезапишут друг друга
}
$unique = array_keys($uniqueMap);  // [1, 2, 3, 4, 5]
```

## 4. Избегаем регулярных выражений, если можно проще

Если задачу можно решить простыми строковыми функциями — используйте их вместо регулярных выражений. Желательно тестировать оба подхода, иногда регулярка может оказаться быстрее.

```php
// ❌ Неправильно: используем regex когда можно проще
if (preg_match('/^Bearer\s(\S+)/', $authHeader, $matches)) {
    return $matches[1] ?? null;
}

// ✅ Правильно: используем простые строковые функции
if (str_starts_with($authHeader, 'Bearer ')) {
    return substr($authHeader, 7);
}
```
## 5. Избегаем неявного поведения

Не предполагайте, что что-то не может вернуться из метода. Явно указывайте возможные типы возвращаемых значений и обрабатывайте их.

```php
// ❌ Плохой код: неявное поведение
public static function getWarningIblockID(): int
{
    // может вернуть 0 если не найдено!
}

public function executeComponent(): void
{
    $data = [];
    $iblockId = GlobalData::getWarningIblockID();
    $iblock = Iblock::wakeUp($iblockId);  // Ошибка если $iblockId = 0
}

// ✅ Хорошо: явное поведение
public static function getWarningIblockID(): int
{
    throw new IBlockNotFoundException('Warning iblock not found');
}

public function executeComponent(): void
{
    try {
        $iblockId = GlobalData::getWarningIblockID();
        $iblock = Iblock::wakeUp($iblockId);
    } catch (IBlockNotFoundException $e) {
        // Правильная обработка ошибки
    }
}
```
**Проблема:**

- `getWarningIblockID` неявно возвращает `0`, если инфоблок не найден.
- Код ниже не обрабатывает случай `0`, что приведёт к фатальной ошибке.
**Решение:**
Метод должен либо возвращать ID, либо выбрасывать исключение, описанное в phpDoc. Это делает поведение явным и ожидаемым.

## 6. Не передаём данные через ассоциативные массивы
Для передачи данных между методами используем:

- DTO
- Массивы DTO
Это упрощает поддержку и даёт автодополнение в IDE.

## 7. Избегаем статики, используем DI
Статика усложняет тестирование и расширяемость. Вместо этого предпочитаем использовать внедрение зависимостей (DI). Статику используем для хэлперов, которые не меняют состояния каких-либо частей системы и не должны содержать бизнес-логики. Также статика используется для фасадов, которые также не должны содержать бизнес-логики. Однако логгер к примеру внедряем все равно через DI, хоть и есть фасад.

## 8. Используем "быстрый выход"

В случае возникновения нештатных ситуаций сразу выбрасываем исключение. Не занимаемся накоплением и обработкой различных ошибочных значений. Не изобретаем дефолтовые неочевидные возвраты из методов. Метод должен возвращать только то, что вытекает из его названия или падать с исключением. Исключения обрабатываются единообразно перехватчиком исключений. Не надо специально обрабатывать неочевидные пустые значения.

```php
// ❌ Плохо: накопление ошибок
public function getUserById(int $id): ?User
{
    if ($id <= 0) {
        return null;
    }

    $user = $this->repository->find($id);
    if (!$user) {
        return null;
    }

    if (!$user->isActive()) {
        return null;
    }

    return $user;
}

// ✅ Хорошо: быстрый выход с исключениями
public function getUserById(int $id): User
{
    if ($id <= 0) {
        throw new InvalidArgumentException('ID must be positive');
    }

    $user = $this->repository->find($id);
    if (!$user) {
        throw new UserNotFoundException('User not found');
    }

    if (!$user->isActive()) {
        throw new UserNotActiveException('User is not active');
    }

    return $user;
}
```
## 9. В запросах никогда не используем *
В SQL-запросах всегда явно указываем нужные поля. Это:

- Уменьшает объём передаваемых данных
- Упрощает понимание кода
- Уменьшает риск проблем при изменении структуры таблиц
