# HOW TO: обработать непойманное исключение в компоненте

> ⚠️ **В текущей версии проекта Rebit P2P Bitrix-компоненты с шаблонами не используются.**
> Фронтенд реализован на Vue 3 + TypeScript + Vite (SPA).
> Этот раздел сохранён как справочный на случай, если компоненты понадобятся в будущем.

Для новых продуктовых компонентов `ExceptionResolver` считается стандартом.
Через него компонент явно описывает своё поведение при непойманной ошибке.

В проекте для этого есть верхнеуровневый механизм:

- `AbstractDtoComponent` ловит `\Throwable`;
- компонент указывает свой `ComponentExceptionResolverInterface`;
- резолвер решает, что делать при ошибке в компоненте.

`DefaultComponentExceptionResolver` существует как технический базовый вариант.
Для обычного продуктового компонента на него не полагаются: вместо этого задают свой resolver с явной деградацией.

## Когда resolver нужен

Обычно resolver нужен, чтобы:

- показать заглушку вместо компонента;
- не рендерить компонент;
- завершить запрос 404;
- сделать redirect.

## Когда без него можно обойтись

Только как исключение.
Например, если это технический компонент, который обязан уронить страницу выше по стеку, и такое поведение заранее согласовано.

## Что есть в механизме

Основные классы:

- `Rebit\Share\Shared\Interface\ComponentExceptionResolverInterface`
- `Rebit\Share\Shared\Dto\ComponentExceptionResolutionDto`
- `Rebit\Share\Shared\Enum\ComponentExceptionActionEnum`
- `Rebit\Share\Shared\Exception\ComponentRedirectException`
- `Rebit\Share\Infrastructure\Bitrix\Resolver\DefaultComponentExceptionResolver`

## Какие действия поддерживаются

`ComponentExceptionActionEnum` поддерживает 4 действия:

- `RENDER_FALLBACK` — показать шаблон заглушки вместо компонента;
- `SKIP_RENDER` — не выводить компонент вообще;
- `PROCESS_404` — завершить запрос через стандартную 404-обработку Bitrix;
- `REDIRECT` — сделать redirect на URL.

## Пример 1. Показать заглушку

Так работает `catalog.section.fast`.

### Шаг 1. Создайте resolver

```php
<?php

declare(strict_types=1);

namespace Rebit\Wallet\Presentation\Component\CatalogSection\ExceptionResolver;

use Rebit\Share\Shared\Dto\ComponentExceptionResolutionDto;
use Rebit\Share\Shared\Interface\ComponentExceptionResolverInterface;
use Psr\Log\LoggerInterface;

final readonly class CatalogSectionExceptionResolver implements ComponentExceptionResolverInterface
{
    private const int HTTP_STATUS_CODE = 503;

    public function __construct(
        private LoggerInterface $logger,
    ) {}

    public function resolve(\Throwable $exception, string $componentName): ComponentExceptionResolutionDto
    {
        $this->logger->error(
            'Ошибка при построении компонента ' . $componentName,
            [
                'componentName' => $componentName,
                'exception' => $exception,
            ],
        );

        return ComponentExceptionResolutionDto::renderFallback(
            templatePath: '/local/templates/.default/components/rebit/shared/catalog_error.php',
            statusCode: self::HTTP_STATUS_CODE,
        );
    }
}
```

### Шаг 2. Подключите resolver в `class.php`

```php
protected function getExceptionResolverClass(): string
{
    return CatalogSectionExceptionResolver::class;
}
```

Результат:

- любое непойманное исключение будет залогировано;
- компонент покажет заглушку;
- HTTP-статус станет `503`.

## Пример 2. Не рендерить компонент

Так работает `catalog.smart.filter.fast` для большинства непойманных ошибок.

```php
<?php

declare(strict_types=1);

namespace Rebit\Wallet\Presentation\Component\SmartFilter\ExceptionResolver;

use Rebit\Wallet\Presentation\Component\SmartFilter\Exception\SmartFilterParsePathException;
use Rebit\Share\Shared\Dto\ComponentExceptionResolutionDto;
use Rebit\Share\Shared\Exception\ComponentRedirectException;
use Rebit\Share\Shared\Interface\ComponentExceptionResolverInterface;
use Psr\Log\LoggerInterface;

final readonly class SmartFilterExceptionResolver implements ComponentExceptionResolverInterface
{
    public function __construct(
        private LoggerInterface $logger,
    ) {}

    public function resolve(\Throwable $exception, string $componentName): ComponentExceptionResolutionDto
    {
        if ($exception instanceof SmartFilterParsePathException) {
            return ComponentExceptionResolutionDto::process404();
        }

        $this->logger->error(
            'Ошибка при построении компонента ' . $componentName,
            [
                'componentName' => $componentName,
                'exception' => $exception,
            ],
        );

        if ($exception instanceof ComponentRedirectException) {
            return ComponentExceptionResolutionDto::redirect($exception->url);
        }

        return ComponentExceptionResolutionDto::skipRender();
    }
}
```

Результат:

- неверный URL фильтра превращается в `404`;
- redirect-case уходит в redirect;
- остальные ошибки скрывают компонент, но не ломают страницу целиком.

## Как передать redirect с runtime URL

Если URL известен только внутри builder, используйте `ComponentRedirectException`.

Пример:

```php
<?php

declare(strict_types=1);

use Rebit\Share\Shared\Exception\ComponentRedirectException;

try {
    $items = $this->smartFilterItemFactory->createItems(
        queryResult: $queryResult,
        sectionsDictionaryById: $propertyValueDictionary,
        sectionsConfig: $config,
        parsedPath: $filter,
        controlItemPrefix: self::CONTROL_PREFIX,
        params: $params,
    );
} catch (\Throwable $e) {
    throw new ComponentRedirectException(
        url: $params->sectionsPath,
        previous: $e,
    );
}
```

Почему так:

- builder знает runtime URL;
- resolver знает только правило деградации;
- `AbstractDtoComponent` централизованно делает сам redirect.

## Что можно ловить локально в builder

Локальный `catch` допустим не для подавления ошибки, а только в 2 случаях:

1. Это отдельный продуктовый сценарий, а не ошибка компонента.
2. Нужно преобразовать низкоуровневое исключение в более понятный верхний сценарий.

Пример продуктового сценария:

```php
try {
    $filter = $this->parseIncomingFilter($params, $propertyValueDictionary);
} catch (SmartFilterUnknownPropertyException) {
    $filter = SmartFilterIncomingFilterDto::createEmpty();
    $isIncorrectFilter = true;
}
```

Это нормальный `catch`, потому что здесь компонент не деградирует в fallback.
Он продолжает обычный поток с другим продуктовым поведением.

Пример преобразования в верхний сценарий:

```php
catch (\Throwable $e) {
    throw new ComponentRedirectException(
        url: $params->sectionsPath,
        previous: $e,
    );
}
```

## Что нельзя делать

Плохо:

- ловить `\Throwable` и просто возвращать `null`;
- логировать и молча проглатывать ошибку;
- делать `LocalRedirect()` прямо в builder;
- вызывать `Tools::process404()` прямо в builder, если это уже policy компонента;
- дублировать одну и ту же деградацию в builder и resolver одновременно.
- рассчитывать, что `DefaultComponentExceptionResolver` сам по себе подходит для обычного продуктового компонента.

Неправильно:

```php
try {
    $data = $this->query->execute($dto);
} catch (\Throwable $e) {
    $this->logger->error('Ошибка', ['exception' => $e]);

    return null;
}
```

Почему:

- ошибка теряется;
- верхний resolver не получает управление;
- поведение компонента размазывается по коду.

## Алгоритм для junior-разработчика

Если вы делаете новый компонент, действуйте так:

1. Сразу определите, как компонент должен деградировать при непойманной ошибке:
   `fallback`, `skip`, `404` или `redirect`.
2. Создайте `ExceptionResolver` под это поведение.
3. Подключите resolver через `getExceptionResolverClass()` в `class.php`.
4. Уберите из builder широкие `catch (\Throwable)`, которые глотают ошибку.
5. Оставьте только узкие `catch`, если это отдельный продуктовый сценарий.
6. Если нужен redirect с runtime URL, бросайте `ComponentRedirectException`.

Оставлять компонент без resolver-а стоит только после явного решения, что он должен падать выше по стеку без собственной деградации.

## Что запомнить

1. Resolver решает, что делать с ошибкой компонента на верхней границе рендера.
2. Builder не должен молча скрывать ошибки через `null`.
3. Product-case можно ловить локально, если это не fallback.
4. Общая деградация компонента должна жить в resolver.
